# Архитектура GeoNexa Proxima

## Цель и границы

GeoNexa Proxima превращает разрозненный научно-технический поток в персональный
ранжированный радар. Ядро не зависит от конкретной БД, модели, Telegram SDK или
внешнего источника. Инфраструктуру можно заменять через контракты в `ports.py`.

Система не должна автоматически считать LLM-ответ фактом: итоговая оценка хранит
причину, а углублённый анализ обязан явно показывать ограничения, данные и
физическую состоятельность.

## Слои

### Домен

`src/geonexa_proxima/domain.py` содержит типы без инфраструктурных зависимостей:

- `CollectedItem` — нормализованный материал до сохранения;
- `StoredItem` — сохранённый материал с оценками;
- `RankResult` — многокритериальное ранжирование;
- `DeepAnalysis` — структурированный глубокий разбор;
- `SearchHit` — результат векторного поиска.
- `User` и `UserProfile` — Telegram identity и независимый исследовательский профиль;
- `ProfileInterest` и `ProfileItemScore` — явные предпочтения и производная
  персональная оценка материала.

### Порты

`src/geonexa_proxima/ports.py` определяет протоколы:

- входные: `Collector`;
- модели: `Embedder`, `Reranker`, `Ranker`, `Analyzer`;
- хранилища: `ItemRepository`, `VectorStore`.
- пользователи: `UserProfileRepository`; профильные векторы хранятся через
  отдельный rebuildable Qdrant adapter.

Прикладной сервис зависит от этих протоколов. Конкретный адаптер зависит от
доменных моделей и реализует протокол, но домен не импортирует адаптер.

### Конфигурация

`Settings` — единственная точка чтения окружения. На границы сервисов настройки
передаются явно. Секреты представлены `SecretStr` и не должны попадать в логи.

### Адаптеры

Ожидаемые группы адаптеров:

- collectors: arXiv, OpenAlex, Crossref, Semantic Scholar, GitHub, Hugging Face;
- persistence: SQLAlchemy/asyncpg для PostgreSQL, Qdrant client для vectors;
- providers: OpenAI-compatible LLM/embeddings и локальные Transformers-модели;
- delivery: FastAPI и aiogram.

## Поток данных

1. Планировщик задаёт окно `since` и лимит каждому collector.
2. Collector возвращает `CollectedItem` в общей схеме.
3. Сервис нормализует идентификаторы и текст, затем выполняет дедупликацию.
4. Repository сохраняет новый материал или связывает его с существующим.
5. Embedder строит вектор `embedding_text`.
6. VectorStore сохраняет вектор и выполняет поиск относительно профиля интересов.
7. Reranker уточняет порядок близких кандидатов.
8. Ranker выставляет оценки 0–10 с объяснением.
9. Analyzer обрабатывает только материалы выше заданного порога или по запросу.
10. API и Telegram выдают дайджест и принимают feedback.

## Пользователи и несколько профилей

Telegram ID является внешней identity, но не профилем. Один пользователь может
иметь несколько именованных профилей, например «Liquefaction ML» и «Numerical
methods». Для интерактивных команд выбирается ровно один активный профиль.
Планировщик независимо обрабатывает каждый профиль с включённым дайджестом.

PostgreSQL хранит исходное описание, явные положительные/отрицательные интересы,
learned feedback-сигналы и версию compiled profile. Qdrant collection
`geonexa_profiles` содержит только кэш profile embeddings. Feedback всегда
связывается с профилем, который сформировал сообщение, а не с профилем, активным
в момент нажатия.

Глобальный ingestion остаётся единым для всех пользователей. На read path
персонализация объединяет:

- 40% — semantic similarity материала и профиля;
- 25% — результат reranker;
- 25% — нормализованный глобальный scientific score;
- 10% — совпадение явных интересов и learned feedback.

Так глобальная научная оценка не смешивается с субъективной релевантностью, а
смена профиля не требует повторно загружать или векторизовать корпус.

## Идентичность и дедупликация

Рекомендуемый порядок ключей:

1. нормализованный DOI;
2. нормализованный arXiv ID без версии;
3. `(source, external_id)`;
4. канонический URL;
5. консервативный fuzzy-match нормализованного заголовка с проверкой даты/авторов.

Нормализация не должна удалять значимые числа, индексы или обозначения методов.
Fuzzy-match не должен автоматически склеивать материалы без дополнительного
сигнала. Оригинальный payload сохраняется в `raw` для аудита.

## Хранение

PostgreSQL — источник истины для метаданных, результатов ранжирования, анализов и
feedback. Qdrant содержит производный векторный индекс и payload для фильтрации.
Qdrant должен быть полностью восстанавливаем из PostgreSQL и выбранной модели.

Размерность collection фиксирована. При смене embedding-модели или размерности
создавайте новую collection, выполняйте переиндексацию и только затем переключайте
чтение.

## Ранжирование

Итоговый `RankResult.total_score` использует:

- 30% — общая релевантность;
- 20% — новизна;
- 15% — научное качество;
- 20% — практическая ценность;
- 15% — важность для AI.

Семантический score используется как сигнал отбора, но не заменяет
многокритериальную оценку. `importance_for_geotechnics` хранится как отдельный
объяснимый сигнал, но текущая MVP-формула не добавляет его повторно в итоговый
score. Таксономия задаёт темы и интересы, а не окончательную истину.

## Режимы моделей

В `api` mode приложение вызывает отдельные inference endpoints. Это основной
вариант для контейнерного API: масштабирование, batching и GPU lifecycle остаются
за пределами веб-приложения.

В `local` mode адаптер загружает веса из `models/`. Такой процесс тяжёлый, требует
ML-группу зависимостей и не должен дублироваться каждым API worker. Для production
предпочтителен один выделенный inference process или внешний сервер.

## Надёжность

- внешние вызовы: timeout, ограниченные retry с backoff и idempotency;
- collectors: checkpoint по источнику, а не одна общая транзакция;
- повторный запуск: безопасный благодаря естественным ключам;
- анализ: version модели, prompt и taxonomy сохраняются с результатом;
- логи: структурированные, без секретов и полных приватных документов;
- health endpoint: проверяет жизнеспособность процесса; readiness отдельно
  отражает доступность обязательных хранилищ.

## Тестовая стратегия

- unit: доменные вычисления, parsing настроек, нормализация и дедупликация;
- contract: каждый adapter против общего набора тестов порта;
- integration: PostgreSQL/Qdrant через Docker;
- API: health, schema и ошибки зависимостей через dependency overrides;
- provider tests: мокированные HTTP-ответы, без реальных токенов и моделей.

Тесты по умолчанию не должны обращаться в интернет, скачивать веса или требовать
GPU.
