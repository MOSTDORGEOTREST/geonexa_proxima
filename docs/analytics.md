# Метрики, статистика и графики

Три отдельные вещи, которые легко перепутать:

| Что | Где живёт | Кто читает |
|---|---|---|
| **Продуктовые метрики** — подписчики, воронка, вовлечённость, расход моделей | суточные роллапы в PostgreSQL | админка |
| **Операционные метрики** — RPS, латентность, ошибки, длина очереди | Prometheus-экспорт на `/metrics` | Grafana / алерты |
| **Сырьё** — события, из которых считается всё остальное | `subscriber_activity`, `harvest_decisions`, `delivery_messages`, `llm_call_log`, `feedback` | роллапы |

Ниже — про первое. Второе — одна строка в `api/app.py` и `PROMETHEUS_ENABLED`.

---

## 1. Почему нужен лог активности

DAU, удержание когорт и «кто из юзеров жив» невозможно восстановить из
состояния: `subscribers.last_seen_at` знает только последний раз. Поэтому
заводится `subscriber_activity` — по строке на осмысленное действие:

```
registered · command · search · feedback · digest_received · link_click
profile_edit · deep_dive · subscription_changed · blocked_bot
chat_joined · chat_left
```

Пишется из бота, из воркеров доставки и из admin API. Индекс
`(occurred_at, subscriber_id)` закрывает и диапазон, и подсчёт уникальных —
проверено `EXPLAIN`: bitmap index scan без похода в таблицу за фильтром.

Индекса по выражению-дате намеренно нет: день считается в `METRICS_TIMEZONE`,
а зона настраиваемая — такой индекс молча перестал бы использоваться при её
смене.

## 2. Роллапы

Запросы дашборда не должны сканировать сырьё. Prefect-флоу `metrics-rollup`
(`METRICS_ROLLUP_CRON`, по умолчанию `15 * * * *`) раз в час пересчитывает
**последние 3 дня** и идемпотентно перезаписывает их через UPSERT — так поздние
данные (доставка, дозагруженные цитирования) попадают в статистику, а история
не переписывается бесконечно.

| Таблица | Разрез | Ключевые поля |
|---|---|---|
| `metrics_harvest_daily` | день × источник | fetched, accepted, borderline, rejected, duplicates, rescued_by_semantic, ranked, analyzed, avg_keyword_score, top_blocked_by |
| `metrics_subscribers_daily` | день × тип | registered, activated, churned, blocked, total, total_active, with_subscription, dau, wau, mau |
| `metrics_delivery_daily` | день × канал | jobs_sent/failed, messages_sent/failed, rate_limited, recipients, avg/p95_queue_seconds, top_errors |
| `metrics_engagement_daily` | день | digests_sent, items_delivered, feedback по видам, unique_reactors, empty_digests, engagement_rate, avg_personal_score |
| `metrics_retention` | когорта × смещение × тип | cohort_size, retained, retention_rate |
| `llm_usage_daily` (из 0003) | день × роль × модель | calls, tokens, reasoning_tokens, cost_usd, errors |
| `metrics_rollup_runs` | — | наблюдаемость самой агрегации: scope, диапазон, статус, длительность, ошибка |

`metrics_rollup_runs` — не бюрократия: без неё «график встал» и «график
правдиво показывает ноль» выглядят одинаково.

### Как считается удержание

Когорта — неделя первого появления (`date_trunc('week', first_seen_at)`).
Удержан на смещении N — есть хотя бы одно событие в `subscriber_activity` на
неделе `cohort_week + N`. Пересчитывается целиком раз в сутки: когорт мало,
инкрементальность тут дороже пересчёта.

## 3. Каталог метрик

### Подписчики

- всего / активных, отдельно люди, группы, каналы;
- регистрации по дням, `pending` в ожидании подтверждения;
- DAU / WAU / MAU и sticky-ratio (DAU/MAU);
- удержание по недельным когортам;
- отток: `blocked`, `left`, `paused`, заблокировавшие бота;
- распределение по планам и статусам подписки, истекающие в ближайшие 7 дней;
- топ подписчиков по активности и по числу фидбеков.

### Воронка сбора

- fetched → keyword-gate → semantic-gate → ranked → analyzed по дням;
- конверсия каждой стадии и разрез по источникам;
- топ `blocked_by` — какая группа стоп-слов режет больше всего;
- термины с нулевым `hit_count` (мёртвый груз) и с аномально высоким (шум);
- средний `keyword_score` принятых и отклонённых — расстояние между ними
  показывает, разделяет ли порог хоть что-то.

### Корпус

- новые материалы по дням, разрез по kind и источнику;
- распределение глобальных оценок;
- доля с доступным кодом и датасетом;
- дубликаты, слитые за период.

### Доставка

- отправлено / провалено по дням и каналам;
- задержка очереди (среднее и p95) — сколько job ждёт воркера;
- топ ошибок Telegram с кодами, доля 429;
- получателей за период.

### Вовлечённость

- дайджестов отправлено, пустых дайджестов;
- фидбек по видам, доля отреагировавших (`unique_reactors / recipients`);
- средний размер дайджеста и средний `personal_score`;
- запросы «разобрать глубже».

### Модели

- вызовы, токены, reasoning-токены и стоимость по ролям и дням;
- доля ошибок и таймаутов, латентность p50/p95;
- стоимость в пересчёте на один дайджест и на одного подписчика.

## 4. Графики

Формы выбраны по задаче данных, палитра прогнана валидатором. Одна ось
всегда: двух шкал Y нет ни на одном графике.

### Палитра

Пока это валидированная эталонная палитра. Когда подставим фирменные цвета
GeoNexa (конструктивистская четвёрка с сайта), значения меняются здесь и
перепроверяются тем же валидатором — метод остаётся прежним.

Поверхности: светлая `#fcfcfb`, тёмная `#1a1a19`. Тёмная тема — отдельно
подобранные шаги той же шкалы, а не автоматическая инверсия.

| Роль | Светлая | Тёмная | Где используется |
|---|---|---|---|
| Серия 1 | `#2a78d6` | `#3987e5` | люди, принято, personal-канал |
| Серия 2 | `#eb6834` | `#d95926` | группы, отклонено |
| Серия 3 | `#1baf7a` | `#199e70` | каналы |
| Ординал 1..5 | `#86b6ef` `#5598e7` `#2a78d6` `#1c5cab` `#104281` | `#184f95` `#256abf` `#3987e5` `#6da7ec` `#9ec5f4` | стадии воронки |
| Секвенциал 100..700 | `#cde2fb` → `#0d366b` | те же шаги, инверсия направления | тепловая карта когорт |
| Диверген − | `#d03b3b` `#ea9a9a` | `#8f2626` `#e06666` | not_interesting |
| Нейтраль | `#f0efec` | `#383835` | середина диверген-шкалы |
| Диверген + | `#86b6ef` `#2a78d6` | `#5598e7` `#9ec5f4` | useful, very_interesting |
| good / critical | `#0ca30c` / `#d03b3b` | те же | статус доставки, всегда с иконкой и подписью |
| Ink / grid | `#0b0b0b` `#52514e` `#898781` `#e1e0d9` | `#ffffff` `#c3c2b7` `#898781` `#2c2c2a` | текст, сетка, оси |

Результаты прогонов `validate_palette.js`:

| Набор | Режим | Итог |
|---|---|---|
| Серии 1–3, `--pairs all` | светлый | PASS · CVD ΔE 9.2 · normal ΔE 24.0 · `#1baf7a` контраст 2.74 → нужны видимые подписи |
| Серии 1–3, `--pairs all` | тёмный | PASS · CVD ΔE 9.4 · normal ΔE 20.9 · контраст ≥ 3:1 |
| Ординал воронки, `--ordinal` | оба | PASS · монотонность, ΔL ≥ 0.06, светлый конец 2.06:1 / 2.15:1 |
| Плечи диверген-шкалы, `--ordinal` | оба | PASS · один тон на плечо, ΔL ≥ 0.06 |

Три светлых оттенка сидят ниже 3:1 к светлой поверхности — на этих графиках
обязательны прямые подписи значений либо табличный вид. Это не пожелание, а
условие, при котором палитра считается прошедшей.

### Спецификация графиков

**Дашборд**

1. **KPI-строка** — четыре stat tile со спарклайном и дельтой: активные
   подписчики, материалов за 7 дней, отправлено сообщений за 7 дней, стоимость
   моделей за 30 дней. Не график — число и есть график.
2. **Воронка сбора за 30 дней** — горизонтальные полосы, ординальная шкала (5
   шагов), прямые подписи с абсолютом и конверсией к предыдущей стадии.
   Категориальную палитру тут нельзя: стадии упорядочены, порядок несёт смысл.
3. **Материалы по дням** — одна серия, площадь, секвенциальный синий. Легенды
   нет: заголовок называет серию.
4. **Доставки по дням** — стопка из двух статусов (good / critical) с иконкой и
   подписью. Статусные цвета не переиспользуются как «серия 4».

**Аналитика → Подписчики**

5. **Рост базы по типам** — стопка площадей, серии 1–3 (люди / группы /
   каналы). Цвет закреплён за сущностью: фильтр по типу не перекрашивает
   оставшихся.
6. **DAU / WAU / MAU** — три линии, одна ось (все три считают людей).
7. **Удержание когорт** — тепловая карта, секвенциальный синий, строки — недели
   регистрации, столбцы — смещение. Значения подписаны в ячейках.
8. **Распределение по планам** — одна горизонтальная стопка part-to-whole,
   не более шести сегментов.

**Аналитика → Контент**

9. **Источники: принято против отклонённого** — форма «акцент»: принятое в
   серии 1, отклонённое в сером. История здесь одна, восемь цветов её похоронят.
10. **Топ причин отклонения** — горизонтальные полосы, все одного тона (серия
    1): категории номинальные, красить их по величине значило бы повторить
    цветом то, что уже показывает длина.
11. **Распределение глобальных оценок** — гистограмма, секвенциальный.

**Аналитика → Вовлечённость**

12. **Фидбек** — диверген-стопка, центрированная на нейтрали:
    not_interesting влево (красное плечо), useful и very_interesting вправо
    (синее плечо). Это порядковая шкала мнения — именно тот случай, для
    которого диверген-форма и существует.
13. **Engagement rate по дням** — одна линия.

**Аналитика → Модели**

14. **Расход по ролям** — стопка по дням, топ-5 ролей плюс «Прочее». Девятый
    цвет не генерируется никогда.
15. **Латентность p50 / p95** — две линии одного тона разной светлоты.

### Общие правила отрисовки

- тонкие марки, скругление 4px на конце данных, линии 2px, маркеры от 8px,
  зазор 2px между сегментами стопки;
- сетка и оси — приглушённые, без пунктира;
- ховер обязателен: перекрестие с тултипом на линиях и площадях, тултип на
  марку на полосах и ячейках;
- при двух и более сериях легенда есть всегда, до четырёх серий — ещё и прямые
  подписи; идентичность никогда не держится на одном цвете;
- у каждого графика есть табличный вид;
- текст носит текстовые токены, а не цвет серии;
- фильтры — одной строкой над графиками, период применяется ко всему разделу.

## 5. API аналитики

```
GET /api/admin/analytics/overview?days=30
GET /api/admin/analytics/subscribers?days=90&kind=&granularity=day|week
GET /api/admin/analytics/subscribers/retention?weeks=12&kind=
GET /api/admin/analytics/subscribers/top?metric=activity|feedback&limit=20
GET /api/admin/analytics/harvest/funnel?days=30&source=
GET /api/admin/analytics/harvest/sources?days=30
GET /api/admin/analytics/harvest/blocked-reasons?days=30&limit=15
GET /api/admin/analytics/harvest/terms?order=hits|dead&limit=50
GET /api/admin/analytics/corpus?days=90&group_by=kind|source|score_bucket
GET /api/admin/analytics/delivery?days=30&channel=
GET /api/admin/analytics/delivery/errors?days=30&limit=15
GET /api/admin/analytics/engagement?days=90
GET /api/admin/analytics/engagement/feedback?days=90
GET /api/admin/analytics/llm?days=30&group_by=role|model|day
GET /api/admin/analytics/export.csv?report=<любой из выше>&...
POST /api/admin/analytics/rollup            -- пересчитать вручную {day_from, day_to, scope}
GET  /api/admin/analytics/rollup/status     -- последние прогоны из metrics_rollup_runs
```

Единый формат ответа временного ряда, чтобы фронт не писал парсер под каждый
эндпоинт:

```json
{
  "granularity": "day",
  "timezone": "Europe/Moscow",
  "from": "2026-08-01",
  "to": "2026-08-30",
  "series": [
    {"key": "user", "label": "Люди", "color_slot": 1,
     "points": [{"t": "2026-08-01", "v": 12}]}
  ],
  "totals": {"user": 340},
  "delta": {"user": 0.12},
  "stale": false,
  "computed_at": "2026-08-30T14:15:00+03:00"
}
```

`color_slot` приходит с бэка, а не выбирается на фронте по индексу массива —
именно так цвет остаётся привязан к сущности при любой фильтрации.
`stale: true` ставится, когда последний успешный роллап старше двух часов:
график должен уметь честно сказать, что данные не свежие.
