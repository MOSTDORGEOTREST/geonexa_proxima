# Эксплуатация Проксимы

## Dev-режим: всё поднимается локально

`docker-compose.dev.yml` поднимает полный стенд, не требуя ни управляемой БД,
ни внешнего Prefect. Базы две: приложение и метаданные Prefect — Prefect
требует отдельную базу, а у управляемой БД Timeweb выдана ровно одна.

```bash
cp .env.example .env          # секреты подставить свои
docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml ps
```

| Сервис | Порт | Что это |
|---|---|---|
| `postgres` | 5432 | PostgreSQL 16 + pgvector (образ `pgvector/pgvector:pg16`) |
| `prefect-postgres` | — | метаданные Prefect, только внутри сети compose |
| `prefect-server` | 4200 | UI и API Prefect |
| `api` | 8000 | FastAPI: health, readiness, webhook, админ-API |
| `bot` | — | long polling aiogram |
| `prefect-worker` | — | исполняет флоу; при старте регистрирует деплойменты |
| `admin-ui` | 5173 | SvelteKit-админка |

В dev по умолчанию `DELIVERY_DRY_RUN=true`: очередь работает целиком, но в
Telegram ничего не уходит — в `delivery_messages` пишутся строки со статусом
`skipped`. Снимать флаг стоит осознанно.

Веса моделей в образ не пекутся. Каталог `MODELS_ROOT` (по умолчанию `models/`)
монтируется внутрь контейнера на чтение; там ожидаются `qwen3-emb-0.6b` и
`qwen3-rerank-0.6b`. Модель ищется по содержимому каталога, а не только по
имени, так что переименование папки не ломает старт.

## Чистая база поднимается сама

Любой сервис при старте берёт advisory-lock, смотрит на схему и при
необходимости накатывает миграции и обязательные записи. Поэтому «поднять
проект на пустой базе» — это `docker compose up`, а не последовательность
ручных команд.

```
wait_for_database        # DB_WAIT_ATTEMPTS × DB_WAIT_DELAY_SECONDS
pg_advisory_lock(8237411)  # один мигрирует, остальные ждут
alembic upgrade head       # если DB_AUTO_MIGRATE
seed_all                   # если DB_AUTO_SEED — идемпотентно
```

Сид кладёт то, без чего система не работает: тариф по умолчанию, harvest-профиль
из `config/harvest.yaml` (7 групп, 323 термина), провайдера и модели LLM с
привязкой восьми ролей, девять расписаний и снимок значений из `.env` в
`app_settings`. Повторный запуск ничего не перезаписывает: существующие строки
пропускаются, и отчёт это показывает.

Что происходит на самом деле, видно в `/ready`:

```json
{"status":"ready","schema":"51 таблиц, ревизия 0005 — актуальна",
 "migrated":false,"pool":{"size":2,"checked_out":0,"overflow":0}}
```

Отключить автоподъём: `DB_AUTO_MIGRATE=false`, `DB_AUTO_SEED=false` — тогда
схему накатывают руками, `poetry run geonexa db upgrade`.

Ручные команды на всякий случай:

```bash
poetry run geonexa db status     # ревизия, число таблиц, состояние пула
poetry run geonexa db upgrade    # alembic upgrade head
poetry run geonexa db seed       # только обязательные записи
```

## Бюджет соединений

Управляемая БД даёт один лимит соединений на всех, а процессов много: `api`,
`bot`, `prefect-worker` и до восьми параллельных флоу подписчиков внутри него.
Поэтому пул маленький и явно ограничен:

```
DB_POOL_SIZE=2
DB_MAX_OVERFLOW=0
DB_CONNECTION_BUDGET=2      # верхняя граница; проверяется на старте
DB_POOL_TIMEOUT=15          # сколько ждать свободное соединение
DB_POOL_RECYCLE=1800        # пересоздавать соединение раз в 30 минут
DB_CONNECT_TIMEOUT=10
DB_COMMAND_TIMEOUT=30       # зависший запрос не держит соединение вечно
```

`DB_POOL_SIZE + DB_MAX_OVERFLOW > DB_CONNECTION_BUDGET` — ошибка конфигурации,
приложение не стартует. Это дешевле, чем упереться в лимит под нагрузкой.

Внутри процесса движок один на DSN (`db/session.py::get_engine`). Восемь
параллельных флоу подписчиков делят один пул, а не открывают восемь. Пул
гасится один раз на остановке сервиса (`dispose_engines`), а не в каждом
контейнере зависимостей — иначе флоу закрывали бы соединения друг у друга.

Что видно снаружи: `/ready` отдаёт `pool`, а `geonexa db status` — то же самое
из консоли. «Висит запрос» и «кончились соединения» выглядят одинаково, но
различаются именно здесь.

## Prefect: расписания и ручной запуск

Источник намерения — таблица `schedules` (её правит админка), источник
исполнения — Prefect. Воркер при старте выполняет
`geonexa prefect deploy`: регистрирует все флоу из каталога
(`flow_catalog.py`) с расписаниями из БД.

Кроны считаются в поясе платформы (`TIMEZONE`, по умолчанию Europe/Moscow), а
не в UTC: пояс уезжает в Prefect вместе со строкой расписания.

| Ключ | Крон по умолчанию | Что делает |
|---|---|---|
| `global-harvest` | `0 1 * * *` | Сбор за последние завершившиеся сутки UTC |
| `digest-dispatch` | выключено | Диспетчер личных дайджестов (`kinds=["user"]`), только вручную |
| `digest-dispatch-chats` | `0 0 * * 1` | Сборка дайджеста групп и каналов, понедельник в полночь |
| `subscriber-digest` | по подписчику | Один профиль; запускается диспетчером |
| `delivery-personal` | выключено | Рассылка в личные чаты, только вручную |
| `delivery-group` | `*/5 * * * *` | Развозит то, что уже можно слать |
| `chat-monitor` | `0 */6 * * *` | Сверка прав бота во всех чатах |
| `subscription-maintenance` | `0 5 * * *` | Истечение подписок и напоминания |
| `metrics-rollup` | `15 * * * *` | Пересчёт суточных агрегатов |
| `maintenance` | `30 4 * * *` | Протухшие и зависшие задания рассылки |

Ритм такой: корпус пополняется каждую ночь по одним суткам, а в чаты уходит
недельная подборка — дайджест собирается в понедельник в полночь и рассылается
в 16:00. Личные чаты живут только на ручном запуске: строки расписания у них
есть, но выключены, и включаются переключателем в админке.

### Почему время рассылки — не крон воркера

Час недельной рассылки задан параметром `deliver_at_hour` у диспетчера чатов:
дайджест ставится в очередь с `scheduled_at` на 16:00, а воркер рассылки
крутится каждые пять минут и просто не видит задание раньше срока.

Соблазнительно было бы поставить воркеру крон `0 16 * * 1` и не гонять его
вхолостую. Так делать нельзя, и вот почему: воркер забирает из очереди одну
пачку (`DELIVERY_BATCH_SIZE`) — всё, что не влезло, ждало бы неделю; а
задание, упавшее на ретрае, ждало бы следующего понедельника и протухло бы
раньше по `DELIVERY_JOB_TTL_HOURS`. Дайджест бы просто не пришёл, и в логе
это выглядело бы как «отправлено».

Ручной запуск диспетчера времени не назначает: администратор нажал кнопку —
значит слать сейчас. Если 16:00 уже прошло, задание тоже уходит сразу.

### Допуск по сроку

Срок следующего дайджеста считается от момента постановки в очередь, а
расписание срабатывает по часам. Прогон в понедельник в 00:00 занял три минуты
— и ровно через неделю профиль «ещё не пора» на эти три минуты, пропускает свой
понедельник и ждёт следующего: недельная рассылка превращается в
двухнедельную. Поэтому диспетчер берёт профили с допуском
`DIGEST_DUE_GRACE_MINUTES` (по умолчанию 90 минут).

### Сбор идёт сутками

Плановый прогон берёт последние завершившиеся сутки целиком. Причина не в
красоте, а в лимитах выдачи — запрос за неделю к arXiv или Crossref упирается
в потолок ответа, и часть материалов молча не доезжает. Воронка при этом
выглядит здоровой, просто корпус беднее, чем должен быть.

**Сутки считаются в UTC, и это принципиально.** Окно уходит источникам их
собственными датными фильтрами: `from_publication_date`/`to_publication_date` у
OpenAlex, `until-pub-date` у Crossref, `pushed:X..Y` у GitHub, `submittedDate` у
arXiv — и все они про UTC. Сутки, сдвинутые в московский пояс, разъезжаются с
этими фильтрами: окно «30 августа по Москве» — это 29-е 21:00 UTC — 30-е 21:00
UTC, источникам уходит запрос за 29-е, соседнее окно спрашивает 28-е и 29-е, а
фильтр по ответу выбрасывает всё, что вышло 30-го. В логе и в отчёте прогона
сутки поэтому подписаны словом UTC.

Прогон в 01:00 по Москве — это 22:00 UTC, поэтому он берёт сутки, которые
закончились накануне: те, что идут прямо сейчас, собрались бы наполовину и
записались бы как собранные целиком.

Если прогоны не отработали (упал воркер, стоял контейнер), следующий добирает
пропущенные сутки по одной — не больше `HARVEST_MAX_CATCHUP_DAYS` (по
умолчанию 7). Откуда продолжать, прогон узнаёт из `harvest_runs.until` —
верхней границы последнего успешного прогона.

```bash
# конкретные сутки и диапазон суток — оба режима есть и во флоу, и в CLI
poetry run geonexa collect --day 2026-08-30
poetry run geonexa collect --since-day 2026-08-18 --until-day 2026-08-20
# запасной режим: одно открытое окно, без нарезки; упирается в лимиты выдачи
poetry run geonexa collect --open-window
```

Диапазон длиннее 90 суток за один прогон отклоняется: это защита от опечатки
в дате, а не ограничение платформы — 2020 вместо 2026 стоит нескольких тысяч
запросов и почти наверняка бана на источниках. Если предел догона отрезал часть
провала, прогон говорит об этом отдельной строкой и печатает готовую команду
для добора: те сутки сами уже не соберутся, граница собранного уедет вперёд.

В хвосте прогона каждый источник называет себя сам: когда стартовал, какое
окно получил, сколько принёс, за сколько секунд и с какой ошибкой упал. Упавший
источник не уносит остальные — сутки закроются, и это осознанный размен:
источник, лежащий неделю, иначе заставлял бы каждую ночь переспрашивать все
четыре и никогда не давал бы корпусу расти. Дыра по нему названа поимённо в
логе и в `stats` прогона, а рядом стоит команда добора.

Отдельная строка появляется, когда источник упёрся в `MAX_ITEMS_PER_SOURCE`:
значит за эти сутки материалов было больше, чем забрано. Заметьте, что у
GitHub и OpenAlex есть собственные потолки на запрос (100 и 200), и лимит выше
них ничего не добавит — постраничного обхода в сборщиках нет.

Из консоли:

```bash
poetry run geonexa prefect deploy                 # зарегистрировать всё
poetry run geonexa prefect run global-harvest     # запустить сейчас
poetry run geonexa prefect schedule               # показать расписания
poetry run geonexa prefect cron global-harvest "0 */4 * * *"
```

Смена расписания сперва пишется в БД, потом отправляется в Prefect. Если
Prefect недоступен, строка помечается `sync_pending=true`, и следующая
синхронизация её дошлёт: расписание, заданное в админке, не теряется от того,
что оркестратор был недоступен минуту. Вместе с расписанием едут параметры
строки — иначе правка вроде «слать в 16:00» доезжала бы до Prefect только при
следующем полном деплое.

**После обновления схемы расписания надо передеплоить.** Миграция правит
строки в БД, но deployment'ы в Prefect живут своей жизнью: перезапуск
`prefect-worker` (он выполняет `geonexa prefect deploy` на старте) или кнопка
досинхронизации в админке переносят правку в оркестратор. Без этого Prefect
продолжит запускать флоу по старому расписанию, а админка будет показывать
новое — расхождение видно по флажку `sync_pending`.

## Production-развёртывание

`docker-compose.yml` рассчитан на внешнюю базу: контейнера PostgreSQL в нём
нет, TLS обязателен, рассылка настоящая, наружу выведен единственный порт —
админка. API и Prefect остаются во внутренней сети.

```bash
cp .env.example .env          # заполнить секреты
docker compose up -d --build
docker compose ps
```

Что обязательно поменять относительно примера:

| переменная | почему |
|---|---|
| `ADMIN_PASSWORD_HASH` | plaintext-пароль в production отвергается на старте |
| `ADMIN_ORIGIN` | без него SvelteKit отвергает POST-формы как CSRF |
| `PUBLIC_BASE_URL` | из него собирается адрес вебхука |
| `DATABASE_SSL_ROOT_CERT` | путь к корневому сертификату внутри контейнера |
| `TELEGRAM_WEBHOOK_SECRET` | иначе вебхук принимает запросы от кого угодно |

Хеш пароля:

```bash
python -c "from argon2 import PasswordHasher; print(PasswordHasher().hash('пароль'))"
```

Хеш кладётся в `.env` и попадает в контейнер через `env_file`, а не через блок
`environment`: значения там проходят подстановку переменных, а argon2-хеш
состоит из долларов (`$argon2id$v=19$m=…`) — compose съел бы его по частям.

Админку публикуйте только за HTTPS: cookie сессии помечается `secure`, и по
HTTP вход просто не сработает.

## Живые проверки

Юнит-тесты не ходят в базу; всё, что связано с параллелизмом и SQL, проверяется
отдельными скриптами против настоящего PostgreSQL. Они заводят временные записи
с меткой прогона и убирают за собой, поэтому их можно запускать и на рабочей
базе — но лучше на стенде.

```bash
poetry run python scripts/check_db.py           # доступность, TLS, btree_gist, права
poetry run python scripts/check_subscribers.py  # подписчики, чаты, подписки, диспетчер
poetry run python scripts/check_delivery.py     # очередь, ретраи, лимиты, уборка
GEONEXA_RUN_INTEGRATION=1 poetry run pytest tests/integration
```

Что именно доказывает каждый:

- `check_subscribers` — личный чат нельзя завести как группу; вторая подписка
  поверх первой отклоняется exclusion-ограничением; канал без права постить не
  попадает ни в адресаты, ни в выборку диспетчера; выгнанного бота видно сразу;
  пробный период выдаётся один раз.
- `check_delivery` — четыре параллельных воркера разбирают очередь без единого
  пересечения; backoff растёт от значения `DELIVERY_RETRY_BACKOFF_SECONDS`;
  задание, пережившее все попытки, признаётся провалившимся; зависшее после
  смерти воркера возвращается в очередь; устаревшие решения гейта удаляются, а
  свежие остаются.
- `check_dispatch` — профиль попадает в выборку, получает срок следующего
  дайджеста и выпадает до его наступления; интервал берётся из тарифа и не
  сокращается настройками профиля; без подписки и на паузе дайджест не
  строится. Самая дорогая ошибка этого узла — не падение, а тишина: без
  переноса срока диспетчер рассылал бы дубликаты на каждом прогоне.
- `check_admin_api` — вход и отказ во входе, защита эндпоинтов токеном, каждый
  GET-эндпоинт против настоящей схемы, создание и удаление подписчика,
  конфликт по `chat_id`, пересечение периодов подписки, проба гейта, разбор
  cron, запрет на правку env-only настроек и запись в аудит. Админка собирает
  запросы строками, и опечатка в имени колонки иначе всплывает у
  администратора в браузере.

## Доступ к боту

`TELEGRAM_REGISTRATION_MODE` решает, кого бот слушает:

| режим | кто проходит |
|---|---|
| `open` | все |
| `allowlist` | `TELEGRAM_ALLOWED_USER_IDS`; **пустой список = все** |
| `invite` | строго `TELEGRAM_ALLOWED_USER_IDS`; пустой список = никто |

`TELEGRAM_OWNER_IDS` проходят при любом режиме — иначе неверная настройка
запирает администратора снаружи, и чинить это приходится через базу.

Пустой список в режиме `allowlist` трактуется как открытый доступ намеренно:
обратное поведение означало бы, что свежая установка молча не отвечает никому,
включая владельца, а по логам это неотличимо от сломанного бота. Сервис пишет
об этом предупреждение при старте.

Групповые чаты выключаются целиком через `TELEGRAM_ALLOW_GROUP_CHATS=false`, а
автозаведение заявки на чат — через `TELEGRAM_AUTO_REGISTER_CHATS=false`.
Во втором случае бота в чат добавят, факт запишется в лог, но заявка не
появится, и подтверждать будет нечего.

Ни то, ни другое не заменяет модерацию: заявка — не доступ. `/start` и
добавление бота заводят подписчика со статусом `pending`, и открывает его
администратор на экране «Заявки». Поэтому свежая установка с открытым режимом
регистрации не начинает рассылать всем подряд: дайджест уходит только тем, кого
пропустили руками.

## Вебхук

В production адрес достаточно указать один раз:

```dotenv
PUBLIC_BASE_URL=https://proxima.example.org
TELEGRAM_WEBHOOK_SECRET=<длинная случайная строка>
```

API при старте сам вызывает `setWebhook` на `<PUBLIC_BASE_URL>/telegram/webhook`
и подписывается на `message`, `callback_query`, `my_chat_member` — последний
обязателен, иначе добавление бота в чат пройдёт мимо платформы.
`TELEGRAM_WEBHOOK_URL` нужен, только если путь отличается.

Адрес на `localhost` вебхуком не станет: Telegram до него не достучится, и
регистрация пропускается — молчаливо зарегистрированный нерабочий вебхук
выглядел бы как исправная настройка.

## Миграции

Перед первым запуском и каждым совместимым релизом:

```bash
poetry run alembic upgrade head
```

Перед production-миграцией:

1. проверьте migration SQL на копии данных;
2. сделайте backup PostgreSQL;
3. оцените lock duration для крупных таблиц;
4. мигрируйте одним экземпляром приложения;
5. запустите smoke test API и фонового pipeline.

Откат схемы выполняйте только если downgrade конкретной миграции проверен.
Откат приложения вперёд- и назад-совместимой схемой безопаснее слепого downgrade.

## Конфигурация production

Обязательные пользовательские значения:

- уникальные `POSTGRES_PASSWORD` и `DATABASE_URL`;
- закрытый Qdrant endpoint и, если используется, `QDRANT_API_KEY`;
- реальные endpoint/model/key для обеих LLM;
- API или local mode для embedder и reranker;
- `TELEGRAM_BOT_TOKEN` и allowlist пользователей;
- публичный HTTPS URL и webhook secret при webhook-режиме.

Секреты храните в secret manager платформы, а не в Compose YAML, image или Git.
Запускайте контейнер от непривилегированного пользователя и ограничивайте сетевой
доступ к PostgreSQL/Qdrant.

## Модели

Для API mode отдельно контролируйте:

- совместимость схемы endpoint с адаптером;
- model ID и revision;
- размерность embeddings;
- timeout, retry и лимиты провайдера;
- политику передачи потенциально чувствительных текстов.

Для local mode:

- заранее скачайте веса через `hf download`;
- проверьте лицензию и checksum/revision;
- измерьте пиковое потребление RAM/VRAM;
- не запускайте несколько worker, каждый из которых загружает свою копию весов;
- прогрейте модель перед включением readiness.

По умолчанию векторы лежат в pgvector (`VECTOR_BACKEND=pgvector`), Qdrant —
альтернативный backend того же порта. Смена embedding-размерности требует
новой коллекции/таблицы. Безопасная схема:

1. создать collection с новым именем;
2. переиндексировать все документы;
3. сравнить полноту и качество поиска;
4. атомарно переключить конфигурацию чтения;
5. удалить старую collection только после периода наблюдения.

## Наблюдаемость

Минимальный набор сигналов:

- количество собранных, новых, дублированных и отклонённых материалов;
- latency/error rate по каждому внешнему источнику и model endpoint;
- длина очереди, возраст последнего успешного pipeline run;
- распределение semantic и total score;
- число глубоких анализов и стоимость LLM;
- размер PostgreSQL и Qdrant collection;
- Telegram delivery success/failure.
- количество активных профилей, время персонального reranking и долю cache hit
  profile embeddings;
- распределение personal score отдельно от глобального scientific score.

Не логируйте API keys, Telegram token, webhook secret и полный `.env`.

## Резервное копирование

PostgreSQL — обязательный backup:

```bash
docker compose exec -T postgres \
  pg_dump -U geonexa -d geonexa -Fc > geonexa.dump
```

Пример восстановления в заранее созданную пустую БД:

```bash
docker compose exec -T postgres \
  pg_restore -U geonexa -d geonexa --clean --if-exists < geonexa.dump
```

Команды содержат локальные имена по умолчанию; подставьте production-реквизиты.
Храните backup зашифрованно и регулярно проверяйте восстановление.

Qdrant — производный индекс, но для быстрого recovery полезны snapshots. Даже при
наличии snapshot должна сохраняться возможность полной переиндексации из
PostgreSQL.

Collection документов задаётся `QDRANT_COLLECTION`, а кэш пользовательских
профилей — `QDRANT_PROFILE_COLLECTION`. Удаление profile collection не приводит
к потере настроек: embeddings будут восстановлены из `subscriber_profiles.compiled_text`
и `version`.

## Пользовательские профили

Регистрация выполняется через `/start` только после прохождения Telegram
allowlist. PostgreSQL хранит минимальные Telegram-атрибуты, профили, явные
интересы и learned feedback. Не записывайте в профиль секретные данные.

Перед миграцией `0002_user_profiles` обязательно сделайте backup: она создаёт
default profile для существующих пользователей, переносит `user_interests` и
добавляет profile attribution к историческому feedback/digests.

Если профиль отредактирован, его `version` увеличивается. Старые
`profile_item_scores` сохраняются для аудита, но не должны использоваться для
нового дайджеста; Qdrant cache с предыдущей версией считается miss.

## Обновление и откат

1. зафиксируйте версии image и model revision;
2. выполните unit и integration tests;
3. сделайте backup;
4. примените миграции;
5. обновите один экземпляр и проверьте health/readiness;
6. разверните остальные экземпляры;
7. проверьте сбор, поиск и доставку Telegram.

При деградации остановите фоновые задания, откатите application image и только
после анализа принимайте решение об откате данных.

## Диагностика

### PostgreSQL недоступен

```bash
docker compose ps postgres
docker compose logs postgres
```

Проверьте, что пароль в `DATABASE_URL` совпадает с `POSTGRES_PASSWORD`. Изменение
переменной после создания volume не меняет пароль уже инициализированной БД.

### Qdrant недоступен

```bash
docker compose ps qdrant
docker compose logs qdrant
curl http://localhost:6333/readyz
```

### API не стартует

Проверьте импорт `geonexa_proxima.api:app`, применённые миграции, readiness
зависимостей и фактические переменные процесса. Health подтверждает работу
HTTP-процесса, но для обработки данных нужен успешный `/ready`.

### Ошибка размерности vectors

`EMBEDDING_DIMENSIONS`, фактический размер вектора модели и размерность Qdrant
collection должны совпадать. Не изменяйте размерность существующей collection
«на месте» — создайте новую и переиндексируйте.
