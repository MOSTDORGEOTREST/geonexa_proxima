# Проксима

Проксима — сервис ГЕОНЕКСЫ: радар научных публикаций, методов, датасетов и
инструментов по инженерной геологии, геотехнике и применению в них ИИ.

Раз в цикл платформа обходит внешние источники, отбирает по глобальному профилю
сбора только то, что относится к делу, нормализует, дедуплицирует, оценивает и
складывает в общий корпус. Дальше для каждого подписчика — человека, группы или
канала — независимо строится персональный дайджест и уезжает в Telegram.

Ключевое отличие от «личного бота»: корпус общий и собирается один раз, а
персонализация делается поверх него. Иначе десять подписчиков означали бы
десять обходов arXiv и десять счетов за LLM.

## Что уже работает

- **Профиль сбора** — 323 термина в семи группах (RU + EN), булево выражение
  допуска, детерминированный keyword-гейт до эмбеддингов: нерелевантное не
  доходит ни до модели, ни до LLM, ни до базы.
- **Общий корпус** в PostgreSQL 16: нормализация, дедупликация, провенанс всех
  источников, векторы в pgvector рядом с метаданными — одна база, одна транзакция.
- **Групп-центричная схема**: субъект — не тот, кто пишет, а чат, в котором
  пишут. Команда в группе работает с профилем группы, личка занимается только
  профилем интересов, а `/start` и добавление бота создают заявку, а не
  подписчика: доступ открывает администратор в админке.
- **Подписчики трёх видов** — личные чаты, группы и каналы — в одной таблице, с
  профилями интересов, подписками (с датами действия и льготным периодом) и
  учётом прав бота в чатах.
- **Десять флоу Prefect**: сбор, два диспетчера дайджестов (лички отдельно от
  чатов), флоу подписчика, два воркера рассылки, мониторинг чатов, обслуживание
  подписок, пересчёт метрик, уборка очереди.
- **Очередь доставки на PostgreSQL** (`FOR UPDATE SKIP LOCKED`), с ретраями,
  экспоненциальным backoff и лимитами Bot API — без Redis.
- **Автоподъём схемы**: чистая база превращается в рабочую при старте контейнера.
- **Реестр моделей**: лёгкая и тяжёлая LLM с отдельными настройками reasoning,
  локальные Qwen3 для эмбеддингов и реранкинга.
- **Сбор идёт сутками**: плановый прогон берёт последние завершившиеся сутки
  UTC и добирает пропущенные дни, если предыдущие прогоны не отработали. Окно
  за неделю упиралось бы в лимит выдачи источника, и часть материалов молча не
  доезжала бы. Сутки именно UTC: датные фильтры у всех четырёх источников —
  тоже UTC, и сутки, сдвинутые в московский пояс, разъезжаются с ними на день.
- **Построчный отчёт по источникам**: в хвосте прогона видно, когда стартовал
  каждый источник, какое окно получил, сколько принёс, за сколько секунд и с
  какой ошибкой упал. Упавший источник не уносит остальные.
- **Курсоры источников**: каждый источник продолжает с того места, где
  остановился, — пропущенный прогон не создаёт дыру, штатный не тащит заново
  уже собранное.
- **Интервал между дайджестами** соблюдается: срок следующего назначается
  после постановки в очередь, а частоту ограничивает тариф — профиль может
  просить реже, но не чаще.
- **Поиск по граням профиля**: профиль ищется и целиком, и каждой темой
  отдельно, а близость берётся максимумом. Иначе профиль из нескольких областей
  превращается в вектор-центроид, и статья, глубоко попадающая в одну тему,
  проигрывает статье, слегка похожей на всё сразу.
- **Обратная связь замкнута**: кнопки под материалом доезжают до планового
  дайджеста, а не только до сообщений, запрошенных командой; нажатия питают
  обучаемый профиль и ленту активности.
- **Форматы дайджеста**: карточки с кнопками в личку, один связный пост в
  канал — с нумерацией, разделами и разбиением по границам материалов.
- **Админка**: FastAPI под `/api/admin` (46 GET-эндпоинтов и операции) плюс
  SvelteKit с дизайн-кодом ГЕОНЕКСЫ. Токен живёт в httpOnly-cookie и в браузер
  не попадает.

Не готово: экспорт Prometheus, шифрование секретов провайдеров в базе, учёт
бюджета токенов. Подробности — в [HANDOFF.md](HANDOFF.md).

## Архитектура

```text
Источники → Collectors → keyword-гейт → нормализация/дедупликация → PostgreSQL
                                     ↓                                  ↓
                              harvest_decisions              Embedder → pgvector
                                                                        ↓
   Профиль подписчика → векторы профиля → Reranker → Ranker/Analyzer → digests
                                                                        ↓
                                          delivery_jobs → воркеры → Telegram
```

Портово-адаптерный подход:

- `domain.py` — доменные модели и словарь: виды подписчиков, статусы бота, оценки;
- `ports.py` — протоколы хранилищ, моделей, сборщиков;
- `config.py` — единственная точка чтения конфигурации;
- `services/` — прикладная логика, не знающая ни про Prefect, ни про aiogram;
- `workflows/` — только оркестрация;
- адаптеры БД и провайдеров реализуют порты и не меняют доменное ядро.

Подробнее: [docs/architecture.md](docs/architecture.md),
[docs/db-schema.md](docs/db-schema.md).

## Требования

- Python 3.11–3.14 (для production рекомендуется 3.12+);
- Poetry 2;
- Docker с Compose plugin;
- для локальных моделей: достаточно диска, RAM/VRAM и ML-зависимости проекта.

## Быстрый старт

Весь стенд поднимается одной командой — включая PostgreSQL с pgvector,
Prefect и админку:

```bash
git clone <repository-url>
cd geonexa_proxima
cp .env.example .env          # подставь свои секреты
docker compose -f docker-compose.dev.yml up -d --build
curl -s localhost:8000/ready | python3 -m json.tool
```

Схему создавать руками не нужно: сервис при старте сам накатит миграции и
засеет обязательные записи (тариф, профиль сбора, реестр моделей, расписания).
Подробности — [docs/operations.md](docs/operations.md).

Без Docker:

```bash
poetry install --with dev
poetry run pytest
poetry run geonexa db upgrade
poetry run geonexa api --reload
```

CLI объявлен как `geonexa`:

```bash
poetry run geonexa --help
poetry run geonexa db status               # ревизия схемы и состояние пула
poetry run geonexa collect                 # один проход сбора
poetry run geonexa digests --kinds user    # дайджесты личных чатов
poetry run geonexa prefect schedule        # что и когда запускается
```

## Настройка окружения

```bash
cp .env.example .env
```

`.env.example` содержит все настройки сервиса с комментариями — это
одновременно шаблон и чек-лист развёртывания; тест не даёт им разойтись.
Значения в нём фиктивные. `.env` в git не попадает.

Минимум для запуска: `DATABASE_URL`, доступы к LLM, `TELEGRAM_BOT_TOKEN` и
учётные данные админки.

Группы переменных:

| префикс | о чём |
|---|---|
| `DATABASE_*`, `DB_*` | подключение, TLS, бюджет соединений, автоподъём схемы |
| `EMBEDDING_*`, `RERANKER_*`, `MODELS_ROOT` | эмбеддинги и реранкинг |
| `LIGHT_LLM_*`, `HEAVY_LLM_*` | дешёвое ранжирование и глубокий анализ |
| `HARVEST_*` | профиль сбора, порог гейта, журнал решений |
| `TELEGRAM_*` | бот, режим доступа, чаты, лимиты Bot API |
| `DELIVERY_*` | очередь: размер пачки, попытки, backoff, TTL |
| `SCHEDULE_*`, `PREFECT_*` | расписания и оркестрация |
| `ADMIN_*` | доступ в админку |
| `METRICS_*` | агрегаты и сроки хранения сырых событий |
| `PERSONAL_*_WEIGHT` | прозрачная формула персонального ранжирования |
| `PROFILE_FACET_*`, `PERSONAL_FACET_*` | поиск по граням профиля: разбор, обход порога, квота |
| `PERSONALIZATION_RERANK_LIMIT` | потолок кандидатов до кросс-энкодера |

Два места, где легко ошибиться:

- **Пароль в `DATABASE_URL` обязан быть percent-encoded.** `{`, `+`, `$`, `?`
  ломают разбор строки подключения.
- **`sslmode` внутри DSN не работает** — asyncpg его не понимает. Режим TLS
  задаётся `DATABASE_SSL_MODE`; конфигурация с `sslmode` в URL отклоняется на старте.

## Модели: три места, где легко потерять качество

### 1. Запросы подаются с инструкцией, документы — без неё

Qwen3-Embedding обучен асимметрично. Запрос оборачивается инструкцией, документ
уходит как есть:

```
Instruct: {задача}\nQuery:{текст запроса}
```

Пробела после `Query:` нет — формат совпадает с карточкой модели и с
`prompts.query` в конфигурации sentence-transformers байт в байт, иначе
локальный и API-режим разойдутся между собой.

Задача настраивается через `EMBEDDING_QUERY_INSTRUCTION`, выключается через
`EMBEDDING_INSTRUCTION_ENABLED=false`. Оба режима — локальный и API —
применяют её одинаково и только к запросам; на это есть тест
(`tests/test_embedding_contract.py`), потому что ошибка здесь ничего не ломает,
а просто тихо стоит несколько процентов качества.

### 2. Размерность, Matryoshka и потолки индексов pgvector

| Модель | Нативная размерность |
|---|---|
| Qwen3-Embedding-0.6B | **1024** |
| Qwen3-Embedding-4B | 2560 |
| Qwen3-Embedding-8B | 4096 |

Matryoshka **режет вектор, но не удлиняет его**: запросить 2560 у модели 0.6B
невозможно. `Settings` отклоняет такую конфигурацию на старте с объяснением, а
не падает потом в неочевидном месте.

Потолки индексов pgvector:

| Тип колонки | HNSW / IVFFlat | Хранение без индекса |
|---|---|---|
| `vector` | **2000** | до 16000 |
| `halfvec` (pgvector 0.7+) | **4000** | до 16000 |

Отсюда три рабочих варианта для 4B:

```dotenv
# а) половинная точность — вектор целиком, индекс работает
EMBEDDING_DIMENSIONS=2560
VECTOR_COLUMN_TYPE=halfvec

# б) обрезка Matryoshka под обычный vector
EMBEDDING_DIMENSIONS=1536
VECTOR_COLUMN_TYPE=vector

# в) полная точность без индекса — только для маленького корпуса
EMBEDDING_DIMENSIONS=2560
VECTOR_INDEX_KIND=none
```

Любая обрезка сопровождается **повторной L2-нормализацией**. Это не
формальность: обрезка ломает единичную норму, а косинус в pgvector и формула
персонализации считают её равной единице.

### 3. Реранкер — не классификатор с головой

Qwen3-Reranker не имеет классификационной головы. Скор берётся как softmax по
логитам токенов `yes` и `no` на последней позиции — именно так он и реализован
в `ml/rerankers.py`.

**GGUF для реранкера брать не нужно.** В llama.cpp известен баг конвертации,
после которого скоры уходят в район 1e-23 и ранжирование превращается в шум.
Рабочие варианты:

```bash
# vLLM
vllm serve Qwen/Qwen3-Reranker-0.6B --task score --port 8002

# либо Infinity / TEI
infinity_emb v2 --model-id Qwen/Qwen3-Reranker-0.6B --port 8002
```

Для эмбеддингов GGUF допустим — баг касается только реранкера.

## Переход на 4B

Смена модели меняет размерность, а размерность зашита в тип колонки. Порядок:

1. **Выбрать вариант размерности** из таблицы выше. По умолчанию — `halfvec`
   на 2560: вектор не режется, индекс работает, память вдвое меньше `vector`.
2. **Проверить версию pgvector.** `halfvec` появился в 0.7:

   ```bash
   poetry run python scripts/check_db.py
   ```

   На более старой версии миграция откажется применяться с объяснением, а не
   упадёт на `CREATE INDEX`.
3. **Скачать веса.** FP16 4B — около 8 ГБ только под параметры, плюс запас на
   KV-cache и токенизатор. На машине без такого запаса берите API-режим.

   ```bash
   hf download Qwen/Qwen3-Embedding-4B --local-dir models/Qwen3-Embedding-4B
   ```
4. **Обновить `.env`:**

   ```dotenv
   EMBEDDING_LOCAL_PATH=models/Qwen3-Embedding-4B
   EMBEDDING_MODEL=Qwen/Qwen3-Embedding-4B
   EMBEDDING_DIMENSIONS=2560
   VECTOR_COLUMN_TYPE=halfvec
   ```
5. **Сделать миграцию колонок.** Тип `vector(1024)` не превращается в
   `halfvec(2560)` сам собой:

   ```sql
   ALTER TABLE item_vectors    DROP COLUMN embedding;
   ALTER TABLE item_vectors    ADD COLUMN embedding halfvec(2560);
   ALTER TABLE profile_vectors DROP COLUMN embedding;
   ALTER TABLE profile_vectors ADD COLUMN embedding halfvec(2560);
   CREATE INDEX ix_item_vectors_embedding_hnsw
       ON item_vectors USING hnsw (embedding halfvec_cosine_ops)
       WITH (m = 16, ef_construction = 64);
   ```
6. **Переиндексировать корпус.** Старые векторы не конвертируются — их нужно
   пересчитать новой моделью:

   ```bash
   poetry run geonexa reindex --all
   ```

   Кэш векторов профилей пересобирается сам при первом обращении: он
   версионированный и не является источником истины.

Пока переиндексация не закончена, семантический поиск отдаёт неполную выдачу.
На большом корпусе разумнее завести вторую пару колонок, наполнить их и
переключиться, а не работать с полупустым индексом.

## Docker

Две конфигурации. `docker-compose.dev.yml` поднимает всё локально, включая
базу; `docker-compose.yml` — production: база внешняя, TLS обязателен,
рассылка настоящая, наружу торчит только админка.

```bash
docker compose up -d --build        # production
docker compose ps
```

Для разработки — весь стенд разом:

```bash
docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml ps
docker compose -f docker-compose.dev.yml logs -f api
```

| Сервис | Порт | Что это |
|---|---|---|
| `postgres` | 5432 | PostgreSQL 16 + pgvector |
| `prefect-postgres` | — | метаданные Prefect (нужна отдельная база) |
| `prefect-server` | 4200 | UI и API Prefect |
| `api` | 8000 | health, readiness, webhook, админ-API |
| `bot` | — | long polling aiogram |
| `prefect-worker` | — | исполняет флоу, регистрирует деплойменты |
| `admin-ui` | 5173 | админка на SvelteKit |

В dev по умолчанию `DELIVERY_DRY_RUN=true`: очередь работает целиком, но в
Telegram ничего не уходит — в `delivery_messages` пишутся строки `skipped`.

Остановить и удалить данные (явно, только по желанию):

```bash
docker compose -f docker-compose.dev.yml down       # оставить данные
docker compose -f docker-compose.dev.yml down -v    # удалить тома
```

Веса моделей в образ не пекутся: каталог `MODELS_ROOT` монтируется на чтение.
Локальные GPU-модели лучше держать отдельным inference-сервисом.

### Если сборка падает

**`poetry install` завершается с кодом 1 сразу после «Installing dependencies
from lock file».** Значит, `poetry.lock` отстал от `pyproject.toml`: кто-то
добавил зависимость и не пересобрал лок. Образ намеренно ставит зависимости
строго по локу — иначе сборка была бы невоспроизводимой и в проде оказалась бы
не та версия, что проверялась.

```bash
poetry lock          # пересобрать лок
poetry check --lock  # убедиться, что сошлось
```

Сборка теперь вызывает `poetry check --lock` первым шагом, поэтому в логе
видно внятное «Run `poetry lock` to fix the lock file», а не голый exit 1.
Тест `tests/test_packaging.py` ловит расхождение ещё до сборки.

**`pip install -e .` падает с `FileNotFoundError: README.md`.** `pyproject`
объявляет README как readme проекта, поэтому файл обязан попасть в образ —
он копируется вместе с `pyproject.toml` и локом.

**`sh: 0: cannot open /usr/local/bin/entrypoint.sh: Permission denied`.**
Контейнер поднимается и сразу падает, healthcheck не успевает ни разу пройти.
Причина не в скрипте, а в правах: `COPY` переносит режим файла с хоста как
есть, и если в рабочей копии `docker/entrypoint.sh` лежит с режимом `600`
или `700`, в образе он оказывается `root:root 700`. `chmod +x` тут не спасает
— он добавляет только бит выполнения (`700` → `711`) и никогда не добавляет
чтение для остальных, а после `USER proxima` скрипт уже некому прочитать.
Поэтому Dockerfile задаёт режим числом: `chmod 0755`. Тест
`test_entrypoint_gets_an_explicit_readable_mode` не даёт вернуть `chmod +x`.

**`dependency failed to start: container ... is unhealthy`.** Компоуз ждал
готовности сервиса и не дождался. Смотреть надо не на эту строку, а на лог
самого контейнера — он единственный говорит, что произошло:

```bash
docker compose -f docker-compose.dev.yml logs --no-log-prefix api | tail -60
docker compose -f docker-compose.dev.yml ps -a          # код выхода
```

Сервис пишет причину сам: строка `Сервис api готов: …` означает, что схема
поднялась; отсутствие такой строки — что упало раньше. Если контейнер жив, но
нездоров, спросите его напрямую:

```bash
docker compose -f docker-compose.dev.yml exec api \
  python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8000/ready').read().decode())"
```

### Режим моделей и сборка образа

Локальные модели тянут `torch` — это примерно 2.5 ГБ в образе, больше, чем всё
остальное вместе взятое. Поэтому по умолчанию их в образе нет, а стенд
работает в API-режиме.

Стенд читает режим из отдельных переменных с префиксом `DEV_`, а не из тех же,
что прод. Это не педантизм: в `.env` лежат production-значения
(`EMBEDDING_MODE=local`), compose подставил бы именно их, и стенд молча
оказался бы в режиме, для которого в образе нет весов. `/health` при этом
остаётся зелёным — модели грузятся лениво, и падает только первый реальный
вызов.

Чтобы использовать веса из `models/`, режим и сборка должны совпадать:

```dotenv
INSTALL_ML=true
DEV_EMBEDDING_MODE=local
DEV_RERANKER_MODE=local
```

```bash
docker compose -f docker-compose.dev.yml build --no-cache api bot prefect-worker
docker compose -f docker-compose.dev.yml up -d
```

Несовпадение не роняет сервис, но и работать он не будет: `/ready` честно
скажет «Веса embedding не найдены» либо что нет `sentence-transformers`, и
останется в состоянии `not_ready` — сбор и дайджесты не пойдут.

Production-процедуры — [docs/operations.md](docs/operations.md).

## Telegram

1. Создайте бота через `@BotFather` и получите токен.
2. Узнайте свой числовой Telegram user ID.
3. Заполните `.env`:

```dotenv
TELEGRAM_BOT_TOKEN=replace-with-real-token
TELEGRAM_OWNER_IDS=123456789
TELEGRAM_REGISTRATION_MODE=allowlist
TELEGRAM_ALLOWED_USER_IDS=123456789,987654321
```

Режим доступа решает, кого бот слушает: `open` — всех, `allowlist` — список
выше, `invite` — строго список. Владельцы из `TELEGRAM_OWNER_IDS` проходят при
любом режиме, чтобы нельзя было запереть себя снаружи. Пустой список в режиме
`allowlist` означает «пускать всех» — сервис предупреждает об этом в логе при
старте, потому что молчащий бот выглядит как сломанный, а не как закрытый.

Для разработки используется polling. Для production достаточно указать внешний
адрес — вебхук регистрируется при старте API сам:

```dotenv
PUBLIC_BASE_URL=https://proxima.example.org
TELEGRAM_WEBHOOK_SECRET=replace-with-long-random-value
```

`TELEGRAM_WEBHOOK_URL` нужен, только если путь отличается от
`/telegram/webhook`. Адрес на `localhost` вебхуком не станет: Telegram до него
не достучится, и регистрация пропускается.

### Кто субъект разговора

Схема групп-центричная: субъект — не тот, кто пишет, а чат, в котором пишут.
В группе и канале команда работает с профилем этого чата, поэтому сотня
участников не заводит сотню подписок и все видят одну и ту же выдачу. В личке
субъект — сам человек, и заниматься там можно только профилем интересов:
материалы приходят в рабочие чаты.

Разделение видно и в меню бота: Telegram получает два разных набора команд —
для личных чатов и для групп (`BotCommandScopeAllPrivateChats` и
`BotCommandScopeAllGroupChats`). Один общий список показывал бы в группе
`/profile_edit`, которого там нет, и в личке `/daily`, который туда ничего не
пришлёт.

### Заявка, а не доступ

Ни `/start`, ни добавление бота в группу не открывают доступ сами по себе.
Оба действия заводят подписчика со статусом `pending`: дайджесты выключены,
диспетчер такую строку не видит (`s.status = 'active'` в выборке), а человек
и чат получают ответ о том, что заявка ушла администратору.

Решение принимается в админке, на экране «Заявки». Подтверждение — одно
действие из пяти шагов: статус `active`, профиль (создаётся, если его нет, и
сразу заполняется описанием интересов), включённый плановый дайджест, пробная
подписка (`DEFAULT_TRIAL_DAYS`, `0` отключает) и сообщение в тот самый чат.
Разносить их по разным кнопкам нельзя: подписчик без профиля, без подписки или с
выключенным дайджестом не попадает в рассылку — просто потому, что так устроен
диспетчер, — и снаружи это выглядит как молчащий бот.

Дайджест включается только чатам. В личку в групп-центричной схеме материалы не
приходят вовсе, и включённый флаг означал бы рассылку, которой не должно быть.

Блокировку выход бота не снимает: `left` не ставится поверх `blocked`. Иначе
заблокированному чату хватило бы выгнать бота и добавить обратно, чтобы
вернуться в рассылку без администратора.

Отметка о подтверждении живёт в `subscribers.meta.approved` отдельно от
статуса. Статус меняется и дальше — чат уходит в `left`, человека ставят на
паузу, — а вопрос «этого вообще когда-нибудь пропускали» после этого теряться
не должен: бота выкидывают и возвращают по бытовым причинам (переезд группы в
супергруппу, чистка администраторов), и требовать подтверждения на каждый такой
случай значит превратить модерацию в шум.

### Личные чаты

Личка — это профиль интересов и ничего больше. После подтверждения приходит
просьба описать интересы обычными словами; дальше работают `/profile`,
`/profile_edit`, `/interests`, `/howto`, а также `/profiles`, `/profile_new`,
`/profile_use`, `/profile_delete` и `/personalization`. Команды дайджеста в
личке отвечают отказом и объясняют, где искать материалы.

`/profile` показывает не только описание, но и темы, на которые оно разбилось,
вместе с замечаниями: разбиение механическое, и увидеть его иначе нельзя.

Весь текст, который видит человек — меню команд, ответы, подписи кнопок,
заголовки дайджеста, — на русском. Кнопки обратной связи под материалом рисует
один модуль `telegram/keyboards.py`, общий для бота и для воркера рассылки:
разъезд между ними означал бы, что кнопка из планового дайджеста не находит
обработчика и обратная связь теряется у всех, кто не запрашивал материал
командой. Тест `tests/test_user_facing_language.py` следит и за языком, и за
этим совпадением.

Описание вроде «я геотехник и занимаюсь ML для разжижения грунтов» становится
частью профиля: оно объединяется с явными интересами и feedback-сигналами и
используется для semantic search, реранкера и объяснения релевантности.
Глобальная научная оценка статьи при этом остаётся общей для всех.

### Поиск по граням профиля

Профиль редко бывает про одну тему. «Математические модели в геотехнике,
механика и разжижение грунтов. Также ИИ в обработке опытов» — это две разные
области, и один вектор на весь текст даёт центроид между ними. Статья, глубоко
попадающая в одну тему, получает средний косинус: центроид оттянут второй темой.
Чем больше у человека интересов, тем сильнее размывание — и тем увереннее
выпадает как раз то, что ему нужнее всего.

Поэтому профиль ищется не одним вектором, а набором:

```text
грань 0  весь профиль целиком          → широкая выборка кандидатов
грань 1  «математические модели…»       ┐
грань 2  «ИИ в обработке опытов»        ├ узкая выборка каждой
грань 3  «разжижение грунтов»  (интерес)┘
                    ↓
     близость = максимум по граням (а не среднее)
                    ↓
     реранкер спрашивает той гранью, которой материал нашёлся
                    ↓
     объяснение и сводку LLM делает по всему профилю
```

Как режется описание: по точкам, точкам с запятой и переводам строк — каждая
строка считается отдельной темой. Жёсткий перенос посреди предложения границей
не считается: строчная буква в начале следующей строки означает, что мысль
продолжается. Слишком короткий обрывок приклеивается к соседнему — искать по
«Также ИИ» нечего, а место в квоте такая грань бы заняла. Каждый явный интерес
из `/interests` тоже становится гранью; отрицательные — никогда: грань это
поисковый запрос, и минус в профиле превратился бы в плюс в выдаче.

Три следствия, ради которых всё и делалось:

- **Максимум, а не среднее.** «Попал в одну тему целиком» перестаёт проигрывать
  «слегка похож на всё сразу».
- **Обход общего порога.** `DIGEST_SCORE_THRESHOLD` стоит на общей научной
  оценке, одинаковой для всех подписчиков, и про личные интересы не знает.
  Косинус выше `PERSONAL_FACET_OVERRIDE_SCORE` (шкала как у
  `SEMANTIC_THRESHOLD`: 0 — ортогонально, 1 — совпадение) пропускает материал и
  с низкой общей оценкой — это и есть случай «в мой интерес попало, а в общем не
  прошло». Смотрится лучшее попадание, и по грани, и по профилю целиком: иначе
  получалась дыра, где материал с косинусом 0.95 по профилю отсекался, а с 0.60
  по грани — проходил. Обход требует, чтобы статья была оценена: `rank is None`
  в дайджесте выглядел бы строкой «без оценки». Выключается значением `1`.
- **Мягкая квота.** `PERSONAL_FACET_MIN_SLOTS` резервирует каждой грани места в
  выдаче, прежде чем остаток разыгрывается по общему баллу. Иначе одна «горячая»
  тема забирает весь дайджест, и остальные интересы человек не видит — при том
  что материалы по ним нашлись и лежат чуть ниже.

Реранкер от этого не дорожает: каждый документ оценивается ровно один раз,
своей гранью, а не общим текстом профиля. Но кандидатов стало больше — восемь
граней тянут свои выборки, — поэтому до кросс-энкодера доживает не всё:
`PERSONALIZATION_RERANK_LIMIT` отсекает хвост по той же формуле личной оценки,
только без вклада реранкера. Без потолка одна рассылка означала бы тысячи пар
«запрос-документ» на профиль.

Окно дайджеста действует и на векторные попадания. Списка «уже отправленного» в
системе нет, и `since` — единственная защита от повторов: без фильтра материал
трёхлетней давности с высоким косинусом приходил бы в каждый недельный дайджест
заново.

Векторы граней лежат в `profile_vectors` с ключом (профиль, версия, грань,
отпечаток текста). Версии мало: номер грани позиционный, и какой текст под ним
окажется, зависит ещё и от `PROFILE_FACET_MIN_CHARS` — смена настройки подсунула
бы под старым номером чужой вектор молча. Отпечаток превращает это в честный
промах кэша. Старые версии убираются при первой же записи: правка профиля и
каждое нажатие кнопки обратной связи поднимают версию, и без уборки таблица
росла бы на набор векторов за клик.

Чем именно материал попал в выдачу, видно в ответе `/why`: там называется
сработавшая грань. `PROFILE_FACET_LIMIT=0` возвращает прежнее поведение с одним
вектором на весь профиль.

### Как писать профиль, чтобы он работал

Профиль выглядит как свободный текст, но обрабатывается механически, и ни одно
из правил из поля ввода не видно. Ошибка в профиле не падает — она молча портит
выдачу месяцами. Поэтому правила живут в трёх местах сразу и в одном
экземпляре: модуль `services/profile_guide.py` отдаёт их и боту по `/howto`, и
админке на экран «Как писать», и API — в виде проверки конкретного профиля.

**Одна область интересов — одно предложение или одна строка.** Описание режется
по точкам, точкам с запятой и переводам строк; каждый кусок ищется отдельно.
Перечисление через запятую в одном предложении останется одной темой, и всё в
нём снова усреднится — то есть ровно то, от чего мы уходили.

```text
✓  Математическое моделирование в геотехнике: МКЭ и определяющие соотношения.
   Разжижение грунтов при циклических нагрузках.
   ИИ для обработки данных полевых и лабораторных опытов.

✗  Интересует геотехника, механика грунтов, разжижение, ИИ и мониторинг
   → одна тема на пять областей
```

**Пишите тему, а не должность.** Тема сравнивается по смыслу с названиями и
аннотациями работ: работает то, что могло бы стоять в заголовке статьи. «Я
главный инженер проекта» в статьях не встречается, «ИИ» похоже на что угодно.

**Явные темы указывайте на двух языках через `;`.** Тема из `/interests`
работает двумя способами: по смыслу (язык не важен, модель многоязычная) и
буквально — точное вхождение в название или аннотацию даёт отдельную прибавку.
Корпус собирается с arXiv, OpenAlex и GitHub и почти весь английский, поэтому
русский термин буквально не совпадёт никогда:

```text
✓  /interests add + 8 liquefaction; разжижение грунтов
✗  /interests add + 8 разжижение грунтов      → буквальной прибавки не будет
```

Для минус-темы это не мелочь, а условие работы: минус существует только ради
буквальной сверки, и без английского написания он не делает ничего. Проверка
профиля помечает такой случай как ошибку, а не как совет.

**Вес 0-10 — это приоритет, а не важность.** Он сравнивает темы между собой:
десятка у всех означает ровно то же, что пятёрка у всех. Рабочий диапазон 3-7,
8-10 стоит оставить одной-двум главным темам.

**Правка заменяет описание целиком** и поднимает версию профиля: темы и их
векторы пересобираются заново. Поэтому правьте осмысленными заходами, а не по
одному слову. Переводы строк при сохранении сохраняются — строка остаётся
границей темы и после перекомпиляции.

Заучивать это не нужно. В админке под полем описания видно, на какие темы оно
разобьётся, и что при этом не сработает — предпросмотр считает тот же код, что
потом будет искать. В боте то же показывает `/profile`, а полную инструкцию —
`/howto`.

### Группы и каналы

Бота добавляют в чат — и он появляется заявкой автоматически (апдейт
`my_chat_member`, `TELEGRAM_AUTO_REGISTER_CHATS=true`; `false` означает, что
заявка не создаётся вовсе и чат игнорируется). В чат при этом уходит короткое
сообщение о том, что бот здесь и ждёт подтверждения: молчащий бот в группе
выглядит сломанным, и через день его выкидывают.

Профиль интересов чата ведёт администратор сервиса — из админки, а не командой
в чате. Иначе любой из сотни участников молча переписывал бы выдачу всем
остальным. Команды профиля, отправленные в группу, отвечают об этом прямо.

Кнопки под материалом при этом работают у всех: реакция относится к профилю
чата, а не к тому, кто нажал. Раньше оценка искалась по подписчику-человеку и в
группе не находилась никогда — снаружи это выглядело как «результат устарел».

Раз в шесть часов `chat-monitor` сверяет права опросом: Telegram сообщает о
выходе бота ровно один раз, и пропущенный апдейт иначе оставил бы чат «живым»
навсегда.

Канал, где боту нельзя постить, не попадает ни в адресаты, ни в выборку
диспетчера: «бот в чате» и «боту есть чем писать» — разные вещи.

### Плановый запуск

```bash
poetry run geonexa digests                      # все виды подписчиков
poetry run geonexa digests --kinds user         # только личные чаты
poetry run geonexa digests --kinds group,channel
poetry run geonexa digests --no-deliver         # собрать, но не отправлять
```

`--no-deliver` оставляет дайджесты в статусе `ready` и ничего не кладёт в
очередь — сухой прогон без единого сообщения. В production этим управляет
Prefect: два диспетчера и два воркера рассылки, у личек и чатов разные лимиты
Bot API и разная частота.

### Регистрация флоу

Контейнер `prefect-worker` при старте сначала регистрирует деплойменты, потом
поднимает воркер. Порядок именно такой, иначе админка увидит пустой список
флоу и не сможет ничего запустить руками. Рабочий пул (`PREFECT_WORK_POOL`,
по умолчанию `geonexa-pool`) создаётся тем же шагом: обычно его создаёт воркер,
но он стартует позже, и на чистой установке регистрация падала бы на
«Work pool not found» — сразу всеми десятью флоу.

Расписания берутся из таблицы `schedules`, а не из кода: админка правит строку,
а деплой переносит правку в Prefect. Источник намерения — база, источник
исполнения — Prefect. Флоу, зарегистрированное без пула, воркер не подберёт
никогда, поэтому пул проставляется явно и проверяется тестом
`tests/test_deployments.py`.

Что должно быть в логе после старта:

```bash
docker compose -f docker-compose.dev.yml logs --no-log-prefix prefect-worker | head -20
```

Ожидается отчёт вида `{"deployed": [...10 ключей...], "skipped": [], "failed": {}}`
и следом `Worker '…' started!`. Непустой `failed` означает, что расписания не
поедут: причина — в тексте рядом с ключом флоу.

## Админка

Открывается по адресу из `ADMIN_ORIGIN` (в dev — `http://localhost:5173`).
Логин и пароль берутся из `.env`; таблицы администраторов нет — хранить
единственного администратора в той базе, которую он чинит, значит потерять
доступ ровно тогда, когда он нужнее всего.

| Экран | Что на нём |
|---|---|
| Дашборд | Счётчики корпуса, подписчиков, подписок и очереди; воронка сбора; материалы и доставки по дням; лента ошибок сбора, доставки и флоу |
| Подписчики | Список с фильтром по виду и статусу, разрез «вид × статус», активация и блокировка |
| Чаты | Группы и каналы с правами бота, ручная сверка через Telegram, проверочное сообщение |
| Подписки | Тарифы, выданные подписки, истекающие за неделю, продление и отмена |
| Сбор | Кнопки «Собрать статьи» и «Собрать за 30 дней» прямо на странице; плашка идущего прогона с кнопкой «Снять прогон»; проба гейта на живом тексте, состав профиля, курсоры источников, топ причин отклонения |
| Доставки | Состояние очереди по каналам, лог заданий, повтор и отмена |
| Расписания | Ручной запуск карточками по этапам конвейера (сбор → дайджесты → рассылка → обслуживание), под ними таблица расписаний с теми же группами, редактор cron с ближайшими запусками, история прогонов |
| Прогоны | История запусков: флоу, состояние, время начала и длительность, фильтры по флоу и состоянию; по строке открывается лог прогона целиком, с подсветкой ошибок, слежением за хвостом и отменой выполняющегося |
| Модели | Провайдеры, модели, привязка восьми ролей с уровнем рассуждения, расход и стоимость |
| Настройки | Все ключи с колонкой «действует», переопределение и сброс к `.env` |
| Аудит | Журнал действий администратора |

Самый полезный экран при настройке — **проба гейта**: вставляете заголовок
реальной статьи и сразу видите, какие термины сработали, какая группа не
выполнилась и почему материал отвергли. Это дешевле, чем узнать о промахе
профиля через неделю по пустому дайджесту.

### Как устроен доступ

Токен администратора не покидает сервер. Страницы собираются серверными
`load`-функциями SvelteKit, которые ходят в FastAPI по внутреннему адресу;
браузер получает лишь httpOnly-cookie. Поэтому наружу торчит только node-слой,
а API и Prefect остаются во внутренней сети compose.

Access-токен живёт 12 часов и обновляется по refresh молча — администратор не
попадает на форму входа посреди заполненной формы. Попытки входа ограничены
(`ADMIN_LOGIN_RATE_LIMIT_PER_MINUTE`), неудачные пишутся в аудит.

Для production вместо `ADMIN_PASSWORD` нужен argon2-хеш — сервис отвергает
plaintext-пароль на старте:

```bash
python -c "from argon2 import PasswordHasher; print(PasswordHasher().hash('ваш-пароль'))"
```

Полученную строку кладите в `ADMIN_PASSWORD_HASH` в `.env`, а `ADMIN_PASSWORD`
оставьте пустым. В `docker-compose.yml` эта переменная приходит через
`env_file`, а не через блок `environment`: хеш состоит из долларов
(`$argon2id$v=19$m=…`), и подстановка переменных compose съела бы его по частям.

## Куда смотреть: порты, адреса, API

Это карта сервиса — что где живёт, на каком порту и каким запросом
проверяется. Порты задаются в `.env` и здесь приведены со значениями по
умолчанию.

### Порты

| Сервис | Dev | Production | Наружу | Что это |
|---|---|---|---|---|
| Админка | `5173` | `3000` | **да, только она** | SvelteKit; единственная точка входа для человека |
| API | `8000` | внутренний | нет | FastAPI: health, вебхук, `/api/admin` |
| Prefect UI | `4200` | внутренний | нет | прогоны флоу, логи, расписания глазами оркестратора. Для повседневной работы не нужен: то же самое, по-русски и без переключения контекста, есть на странице «Прогоны» в админке |
| PostgreSQL | `5432` | внешний | нет | в dev поднимается в compose, в production — управляемый |
| Prefect-БД | — | — | нет | метаданные оркестратора, только внутри сети |

В dev наружу открыты все порты — так удобнее отлаживать. В production
`docker-compose.yml` публикует **только админку**: API и Prefect остаются во
внутренней сети compose, и достучаться до них можно лишь изнутри
(`docker compose exec`) либо через SSH-туннель.

Открыть Prefect UI из production, не публикуя порт:

```bash
ssh -L 4200:localhost:4200 сервер   # затем http://localhost:4200
```

### Первое, что стоит проверить

```bash
curl -s localhost:8000/health              # живой ли процесс
curl -s localhost:8000/ready | jq          # готов ли работать
```

`/health` отвечает всегда, пока жив HTTP-процесс, — это проба для
балансировщика. `/ready` отвечает по существу: состояние схемы, пул
соединений и что именно не готово.

```json
{
  "status": "ready",
  "components": {"repository": true, "embedder": true, "vector_store": true, "...": true},
  "schema": "51 таблиц, ревизия 0005 — актуальна",
  "migrated": false,
  "pool": {"size": 2, "checked_in": 2, "checked_out": 0, "overflow": 0}
}
```

`status: not_ready` — не поломка, а диагноз, и в поле `error` написан
конкретный: «Веса embedding не найдены: ни по пути models/Qwen3-Embedding-0.6B,
ни в models (каталог пуст)». Смотреть на `pool`: «висит запрос» и «кончились
соединения» снаружи выглядят одинаково, а различаются именно здесь. Пул
показывается даже когда сервис не готов, — состояние базы в такой момент нужно
видеть сильнее всего.

### Admin API

Всё под `/api/admin`, всё кроме входа требует `Authorization: Bearer <token>`.

Получить токен:

```bash
TOKEN=$(curl -s localhost:8000/api/admin/auth/login \

curl -s localhost:8000/api/admin/dashboard/summary -H "Authorization: Bearer $TOKEN" | jq
```

### Запустить руками

На странице «Расписания» ручной запуск вынесен наверх и разложен по этапам
конвейера — сбор, подготовка дайджестов, рассылка, обслуживание. Кнопки
названы тем, что они делают («Собрать статьи», «Разослать в группы и каналы»),
а не ключами флоу; под каждой написано, чем она отличается от соседней.
Названия этапов лежат в одном месте — `admin-ui/src/lib/flows.ts`, — и таблица
расписаний группируется по тем же этапам, поэтому разъехаться они не могут.

Две кнопки продублированы там, где их ищут: «Собрать статьи» и «Собрать за
30 дней» стоят на странице «Сбор». Первая повторяет обычный прогон по
расписанию, вторая берёт окно в 720 часов и до 200 материалов с источника —
это способ догнать источники после простоя, он заметно дольше и дороже по
токенам.

Кнопки выключены, пока Prefect не отвечает: задание некуда поставить, и
честнее сказать это сразу, чем принять нажатие в пустоту.

### Наблюдать за прогоном

Страница «Прогоны» отвечает на три вопроса, ради которых иначе пришлось бы
идти в Prefect UI: что запускалось, чем закончилось и сколько заняло. Строки
с состоянием `выполняется` обновляются сами каждые пять секунд, пока прогон не
завершится; когда всё закончилось, опрос прекращается.

По строке открывается лог этого прогона — полностью, а не первые двести строк:
Prefect отдаёт не больше двухсот за запрос и отвечает 422 на просьбу дать
больше, поэтому клиент листает страницами. Интересен как раз конец, где
написано, что сломалось. Уровни `ERROR` и `WARNING` подсвечены, «следить за
хвостом» прокручивает к последней строке по мере поступления, выполняющийся
прогон можно отменить.

Запланированные прогоны на этой странице видны (счётчик «в очереди»), но в
«Последних прогонах» на странице расписаний — нет: у них нет времени старта,
Prefect сортирует по нему, и двадцать «запланирован» вытеснили бы из выборки
последний настоящий прогон.

Если Prefect недоступен, список берётся из локального зеркала `flow_runs`:
состояния и время там есть, логов нет — они живут только в оркестраторе, и
страница об этом честно пишет.

### Что смотреть, когда что-то не так

| Симптом | Куда смотреть |
|---|---|
| Сервис не поднимается | `curl localhost:8000/ready` — поле `error` называет причину |
| Бот молчит | `/api/admin/health` → `telegram`; затем режим доступа: пустой allowlist пускает всех, `invite` с пустым списком — никого |
| Команда бота не отвечает | `curl localhost:8000/ready` → `components`: `false` у `embedder`, `vector_store` или `profile_vector_store` означает, что персонализация не собрана, и `/daily` физически нечем построить. Сам бот теперь отвечает на любую упавшую команду и пишет трейсбек в лог: `docker compose -f docker-compose.dev.yml logs bot` |
| Админка показывает «Internal Server Error» | Это баг, а не состояние: «не нашлось» отдаётся как 404 с текстом, недоступный Prefect — как 503. Пятисотка означает необработанное исключение, смотреть `logs api` |
| Дайджесты не уходят | `/api/admin/deliveries/queue` — если растёт `queued`, воркер не забирает; если `stuck` — воркер умер между claim и отправкой |
| Дайджест ушёл дважды | `/api/admin/deliveries/jobs?subscriber_id=…`; повторная постановка того же дайджеста игнорируется, так что дубликат означает два разных дайджеста |
| Сбор ничего не находит | `/api/admin/harvest/blocked-reasons` — что именно отсекается; потом `/harvest/test` на конкретном заголовке |
| «duplicate key ... uq_harvest_runs_running» | Предыдущий сбор не закрыл свою запись — упал воркер или убили контейнер. Одновременно идёт только один прогон, поэтому незакрытая запись блокирует следующие. Сбор подбирает такие сам: перед стартом закрывает всё, что висит дольше `HARVEST_RUN_STALE_MINUTES` (по умолчанию 90 мин), и помечает как неудачное. Если прогон идёт по-настоящему, сообщение назовёт его id и время старта — снять его можно кнопкой «Снять прогон» на странице «Сбор» — она появляется, только когда прогон есть |
| Собирается мусор | `/api/admin/harvest/decisions?decision=accepted` — что прошло гейт и по каким терминам |
| Источник замолчал | `/api/admin/harvest/cursors` — водяной знак стоит на месте |
| Флоу не запускается | `/api/admin/prefect/health`; при недоступном Prefect расписания помечаются `sync_pending` и досылаются позже |
| «Не синхронизировано» у всех расписаний | Деплойменты не зарегистрированы: `logs prefect-worker` покажет отчёт с непустым `failed`. Кнопка «Запустить» в этом состоянии отвечает 404 с объяснением, а не пятисоткой |
| Кончаются соединения | `/ready` → `pool`: `checked_out` упирается в `size` |
| Дорого | `/api/admin/llm/usage?group_by=role` — какая роль сколько тратит |

### Логи

```bash
docker compose logs -f api            # HTTP, бутстрап, вебхук
docker compose logs -f bot            # команды и апдейты Telegram
docker compose logs -f prefect-worker # исполнение флоу
```

В production логи в JSON (`LOG_JSON=true`) — их читает сборщик, а не человек;
в разработке — человекочитаемые. Уровень задаётся `LOG_LEVEL`.

### Прямо в базу

```bash
docker compose exec postgres psql -U geonexa -d geonexa   # dev
```

Три запроса, которые отвечают на большинство вопросов:

```sql
-- Кому и когда положен следующий дайджест
SELECT s.title, p.name, p.digest_enabled, p.last_digest_at, p.next_digest_at
  FROM subscriber_profiles p JOIN subscribers s ON s.id = p.subscriber_id
 ORDER BY p.next_digest_at NULLS FIRST;

-- Что происходит в очереди прямо сейчас
SELECT channel, status, count(*), min(scheduled_at) AS ждёт_с
  FROM delivery_jobs GROUP BY 1, 2 ORDER BY 1, 2;

-- Почему материалы не проходят гейт
SELECT coalesce(blocked_by, 'не прошёл satisfy') AS причина, count(*)
  FROM harvest_decisions WHERE decision = 'rejected'
   AND created_at > now() - interval '7 days'
 GROUP BY 1 ORDER BY 2 DESC;
```

## Тесты и качество

```bash
poetry run pytest                    # не требует ни .env, ни базы
poetry run ruff check .
poetry run ruff format --check .
```

Юнит-тесты изолированы от окружения: `tests/conftest.py` фиксирует конфигурацию,
поэтому прогон на чистом клоне без `.env` даёт тот же результат, что и у вас.

Проверки против настоящего PostgreSQL — отдельно, они меняют данные:

```bash
poetry run python scripts/check_db.py           # доступность, TLS, права
poetry run python scripts/check_subscribers.py  # подписчики, чаты, подписки
poetry run python scripts/check_delivery.py     # очередь, ретраи, уборка
poetry run python scripts/check_admin_api.py    # все эндпоинты админки
GEONEXA_RUN_INTEGRATION=1 poetry run pytest tests/integration
```

`check_admin_api.py` заслуживает отдельного слова: админка собирает запросы
строками, и опечатку в имени колонки не поймает ни линтер, ни тест с
заглушкой — она всплывёт, когда администратор откроет экран. Скрипт логинится
и дёргает каждый GET-эндпоинт против настоящей базы; любой 500 означает, что
SQL разошёлся со схемой.

Админка проверяется своей сборкой:

```bash
cd admin-ui && npm install && npm run build
```

Скрипты заводят временные записи с меткой прогона и убирают за собой.

## Безопасность

- никогда не коммитьте `.env`, токены, дампы БД и загруженные модели;
- ограничивайте бота режимом доступа — открытый радар оплачивается вашими
  ключами к LLM;
- отдельные пароли БД для production, `ADMIN_PASSWORD_HASH` вместо plaintext
  (сервис отвергает plaintext-пароль в production на старте);
- админку публикуйте только за HTTPS: cookie сессии помечается `secure`
  в production, и по HTTP вход просто не сработает;
- не публикуйте PostgreSQL, FastAPI и Prefect напрямую в интернет — в
  production-compose наружу выведена только админка;
- pin-те revision моделей для воспроизводимого развёртывания;
- соблюдайте rate limits и лицензии источников.
