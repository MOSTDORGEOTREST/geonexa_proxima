# Передача проекта: Проксима

## Где проект сейчас

Платформа собрана и проверена против настоящего PostgreSQL: общий профиль
сбора, подписчики трёх видов, подписки, очередь доставки, десять флоу Prefect,
автоподъём схемы на чистой базе, курсоры источников, два формата дайджеста,
admin API и админка на SvelteKit. Не построены экспорт Prometheus, шифрование
секретов провайдеров в базе и учёт бюджета токенов.

Первый прототип (один пользователь, один флоу) полностью вытеснен: его модули
удалены, документ по его архитектуре — тоже.

Документы v2:

- [docs/architecture.md](docs/architecture.md) — архитектура, каталог
  Prefect-флоу, реестр моделей, слои кода;
- [docs/operations.md](docs/operations.md) — dev-режим, автоподъём схемы,
  бюджет соединений, запуск флоу из админки;
- [docs/db-schema.md](docs/db-schema.md) — схема БД v2, 18 новых таблиц,
  порядок миграции;
- [docs/admin.md](docs/admin.md) — admin API и админка на SvelteKit;
- [docs/analytics.md](docs/analytics.md) — метрики, роллапы, спецификации
  графиков;
- [docs/design.md](docs/design.md) — дизайн-код: токены, шрифты, виджеты,
  логотип и палитра данных;
- [config/harvest.yaml](config/harvest.yaml) — глобальный профиль сбора.

## Фундамент

- типизированные настройки, доменные модели, порты, DI-контейнер;
- collectors arXiv / OpenAlex / Crossref / GitHub + Semantic Scholar enricher;
- нормализация, дедупликация, provenance источников;
- PostgreSQL-схема, async-репозитории, Alembic 0001–0005;
- pgvector для материалов и версионированный кэш векторов профилей
  (Qdrant остался альтернативным backend за тем же портом);
- Qwen3 Embedding/Reranker (local и api), OpenAI-совместимые LLM-клиенты;
- пайплайн сбора, FastAPI, CLI, Telegram polling/webhook;
- профили интересов, персональное ранжирование, feedback loop.

## Платформа

- **Профиль сбора `geo_ai_core`** — 323 термина в семи группах (геотехника и
  инженерная геология, AI/ML, мониторинг и ДЗЗ, сигналы качества, жёсткие и
  мягкие стоп-слова), RU + EN, булево выражение допуска
  `geo_domain and (ai_method or geo_sensing) and not hard_exclude`,
  шаблоны запросов по пяти источникам, список приоритетных журналов.
- **`src/geonexa_proxima/harvest/matcher.py`** — детерминированный keyword-gate:
  нормализация текста, четыре типа матчинга (phrase / token / prefix / regex),
  безопасный вычислитель satisfy-выражения (только and/or/not над id групп,
  произвольный код отклоняется), взвешенный `keyword_score` с покрытием и
  штрафом за мягкие стоп-слова, объяснение решения со списком сработавших
  терминов. 21 тест на реальных формулировках заголовков — 0 промахов на
  контрольной выборке из 14 релевантных и нерелевантных статей.
- **Миграция `0003_platform_v2`** — прогнана на живом PostgreSQL 16:
  `upgrade head` → `downgrade 0002` → `downgrade base` → `upgrade head` без
  ошибок, 42 таблицы. Проверено поведение exclusion constraint на подписках
  (пересечение периодов отклоняется) и CHECK на знак chat_id. Заодно
  исправлен двойной префикс имён CHECK, унаследованный из 0001
  (`ck_digests_ck_digests_status` → `ck_digests_status`).
- **Подключение к управляемой БД Timeweb** — `src/geonexa_proxima/tls.py`
  собирает `ssl.SSLContext` из режима и корневого сертификата; `Settings`
  отклоняет `verify-*` без CA, отсутствующий файл сертификата и `sslmode`,
  забытый внутри DSN. Проверено на PostgreSQL 16 с настоящим TLS: `disable`,
  `require`, `verify-ca`, `verify-full` проходят, а `verify-full` с чужим CA
  честно падает. Alembic ходит через тот же контекст — миграции прогнаны по
  зашифрованному каналу.
- **`scripts/check_db.py`** — предполётная проверка: доехали ли, шифруется ли
  канал, чем занята база, есть ли `btree_gist` и права на `CREATE`/`CREATEDB`.
- **Миграция `0004_metrics`** — событийный лог `subscriber_activity`, пять
  таблиц суточных роллапов, когорты удержания и `metrics_rollup_runs`. Полный
  round-trip 0001→0004 и обратно на живой БД, 49 таблиц. Запросы DAU/WAU/MAU и
  удержания по когортам проверены на засеянных данных, `EXPLAIN` подтверждает
  работу составного индекса.
- **Дизайн-код** перенесён с сайта: токены «Amber & Forest», Unbounded / Inter /
  JetBrains Mono, спецификации виджетов. Логотип — эмблема ГЕОНЕКСА, имя
  продукта — Проксима. Шрифты (19 WOFF2) и обе версии эмблемы скопированы в
  `admin-ui/static/`.
- **Палитра данных** выведена из фирменных тонов и прогнана валидатором: в
  светлой теме слоты 1 и 2 — буквально токены `--amber` и `--emerald-d`.
  Выяснилось, что янтарь и красный эмблемы разнесены всего на 43° и как
  соседние серии проваливают порог различимости, поэтому красный остаётся
  статусом, а категориальных слотов честно три. Числа — в
  [docs/design.md](docs/design.md).
- **`.env`** — 138 переменных с рабочими секретами; `.env.example` — тот же
  файл без секретов.

## Бэкенд: предыдущий заход

- **`Settings` дописан целиком** — 133 поля, читает все 151 переменную `.env`.
  Валидаторы отклоняют на старте то, что иначе всплыло бы в проде: размерность
  выше нативной у модели, размерность не помещающуюся в индекс pgvector,
  `sslmode` внутри DSN, plaintext-пароль админки в production, `verify-*` без
  корневого сертификата.
- **Слой эмбеддингов приведён к контракту модели.** Инструкция уходит только с
  запросом, документы — без неё, формат совпадает с карточкой модели байт в
  байт. Работает одинаково в локальном и API-режиме, покрыто десятью тестами.
- **Векторы переехали в pgvector.** Адаптер `PgVectorStore`, тип колонки
  `Vector` для SQLAlchemy, миграция `0005`. Проверено на живой базе: точный
  ближайший сосед с косинусом 1.0000 на 300 векторах, `EXPLAIN` подтверждает
  работу HNSW-индекса, гард отказывает при попытке подсунуть другую размерность.
- **ORM-модели под 0003/0004/0005** — 50 таблиц. `alembic check` говорит
  «No new upgrade operations detected»: модели совпадают с базой один в один.
- **Очередь доставки на PostgreSQL.** Проверено четырьмя параллельными
  воркерами: 30 заданий разобраны без единого пересечения, повторная постановка
  того же дайджеста игнорируется, backoff и признание провала после исчерпания
  попыток работают, зависшие после смерти воркера задания возвращаются в очередь.
- **Пять Prefect-флоу**: `global-harvest`, `digest-dispatch` →
  `subscriber-digest`, `delivery-personal`, `delivery-group`,
  `metrics-rollup`. Логика вынесена в сервисы, флоу только оркеструют.
- **Агрегаты метрик** — четыре запроса (воронка, подписчики с DAU/WAU/MAU,
  доставка, когорты удержания). Все прогнаны на живых данных и идемпотентны:
  повторный прогон за то же окно не плодит строк.
- Тесты: 67 проходят, `ruff` чист, миграции 0001→0005 туда-обратно по
  зашифрованному каналу без ошибок.

## Поиск по граням профиля

- **Проблема.** Профиль из нескольких областей в одном векторе — это центроид
  между ними. Статья, глубоко попадающая в одну тему, получает средний косинус,
  потому что центроид оттянут остальными темами; чем больше у человека
  интересов, тем увереннее выпадает как раз то, что ему нужнее всего. Отдельно
  добивал общий научный порог: он одинаков для всех подписчиков и про личные
  интересы не знает.
- **Решение.** `services/facets.py` режет `compiled_text` на грани (предложения
  описания плюс каждый положительный явный интерес), `PersonalizationService`
  ищет и полным профилем, и каждой гранью, близость берёт максимумом, реранкер
  спрашивает той гранью, которой материал нашёлся, а объяснение LLM строит по
  всему профилю.
- **Отрицательные интересы гранями не становятся.** Грань — это поисковый
  запрос: минус в профиле превратился бы в плюс в выдаче.
- **Обход порога** (`PERSONAL_FACET_OVERRIDE_SCORE`) пропускает материал с
  низкой общей оценкой при сильном попадании в грань, но требует, чтобы статья
  была оценена: `rank is None` в дайджесте выглядел бы строкой «без оценки».
- **Мягкая квота** (`PERSONAL_FACET_MIN_SLOTS`) резервирует каждой грани места
  в выдаче: иначе одна «горячая» тема забирает весь дайджест.
- **Кэш векторов** — `profile_vectors` с ключом (профиль, версия, грань),
  миграция 0006. Без кэша каждая рассылка перевычисляла бы по вектору на каждую
  грань каждого профиля; недостающие грани эмбеддятся одной пачкой
  (`Embedder.embed_queries`).
- **Реранкер не дорожает**: число пар «запрос — документ» то же, просто вызовов
  столько, сколько задействовано граней.
- `PROFILE_FACET_LIMIT=0` возвращает прежнее поведение с одним вектором.
- Проверено на живом PostgreSQL 16 с pgvector: 0001→0006 и обратно, `alembic
  check` чист, запись и чтение `matched_facet` и векторов граней.
- Не сделано: грани не показываются в админке отдельным списком, а `/search`
  по-прежнему ищет полным профилем.

## Что нашёл разбор перед продом

Ниже — дефекты, найденные сквозной проверкой уже написанного, и то, чем каждый
из них проявлялся бы. Все закрыты; на каждый есть тест.

**Тихо не работало вовсе.**
- Подтверждение чата не включало `digest_enabled`, а профиль заводится
  выключенным. Диспетчер отбирает по этому флагу: подтверждённый чат не получал
  ничего, и по статусу это неотличимо от работающего. Личке дайджест не
  включается намеренно — в групп-центричной схеме материалы туда не идут.
- Кэш векторов граней записывался с отпечатком, а читался без него: правка
  ушла не в тот файл. Кэш не совпадал бы никогда, и каждая рассылка
  пересчитывала бы все векторы заново. Поймал тест, а не чтение кода.

**Портило данные.**
- Карточка подписчика не отдавала `description`, редактор показывал пустое поле
  и сохранял его обратно как осознанную очистку: любое сохранение стирало
  описание, по которому работает весь отбор. Теперь колонка в выборке, а тест
  `test_editor_can_read_back_every_field_it_writes` сверяет, что редактор не
  может записать поле, которого не читает.
- Нормализация описания схлопывала переводы строк. Строка — граница темы, и
  профиль «по теме на строку» при следующей перекомпиляции склеивался в одну
  тему; внешне текст оставался прежним. Появился `clean_description`.

**Портило выдачу.**
- Окно `since` не применялось к векторным попаданиям, а списка «уже
  отправленного» в системе нет: старый материал с высоким косинусом возвращался
  бы в каждый недельный дайджест вечно.
- `PERSONAL_FACET_OVERRIDE_SCORE` описывался косинусом, а сравнивался с
  приведённой шкалой, где ортогональный материал равен 0.5. Значение вроде 0.45
  означало бы «пропускать вообще всё», молча. Теперь косинус и `gt=0`.
- Обход порога смотрел только на грани: материал, найденный профилем целиком с
  косинусом 0.95, отсекался, а найденный гранью с 0.60 — проходил.
- Запасная семантическая оценка бралась из `item.semantic_score` — это близость
  к общему профилю сбора, смешанная с вероятностью реранкера при загрузке.
  Материал, которого не нашёл никто, обгонял по семантике настоящее попадание.
- Порог личной оценки применялся вызывающим кодом после квоты: место,
  зарезервированное слабой гранью, пропадало, и дайджест приходил короче.
- Кэш векторов ключевался только версией профиля, а номер грани позиционный:
  смена `PROFILE_FACET_MIN_CHARS` подсовывала под старым номером чужой вектор.
  Поиск шёл по прошлому тексту, а объяснение называло новую тему.
- `split_sentences` склеивал соседние темы встык через перевод строки
  («нагрузках.ИИ»), а попытка чинить это пробелом ломала «2.5» — теперь
  разделители остаются внутри куска.

**Могло лечь под нагрузкой.**
- До кросс-энкодера доходило до 520 материалов на профиль вместо прежней сотни,
  а при предельных настройках — 18 000. Появился `PERSONALIZATION_RERANK_LIMIT`.
- `VECTOR_HNSW_EF_SEARCH=80` был меньше выборки в 100: HNSW возвращает не больше
  `ef_search` соседей, и пятая часть выдачи терялась без ошибки. Дефолт поднят
  до 120, расхождение теперь ловит валидатор на старте.
- Карточка `/profile` и `/howto` собирались в сообщения без учёта лимита Bot
  API: длинный профиль означал отвергнутый ответ, шесть сообщений подряд —
  `429`. Появился `chunk_messages`.

**Врало администратору.**
- Блокировку чата снимал выход бота: `left` ставился поверх `blocked`, а возврат
  видел только `left` и открывал доступ.
- Экран чатов писал «приветствие отправлено» независимо от того, прошло ли оно.
- Недоступный API рисовался как пустая очередь заявок и пустой список чатов, а
  падение базы — как «подписчик не найден».
- Предпросмотр профиля при ошибке показывал «замечаний нет» — экран, который
  существует ради поиска ошибок, молча провалившийся.
- Отказ не попадал в историю чата, в отличие от подтверждения.
- Пустое числовое поле уезжало как `0`: очищенный «Порог» ставил
  `min_personal_score = 0`, то есть «пропускать всё».

**Пре-existing, поправлено заодно.** Неизвестный разрез метрик ронял флоу
`KeyError` внутри той же транзакции, в которой писалась строка `running`: она
откатывалась, и прогон исчезал из `metrics_rollup_runs` целиком.

**Осталось как есть, осознанно.** `subscriber_profiles.kinds` и
`min_global_score` не читаются нигде — в плановом пути диспетчер всегда берёт
глобальный порог. Пять колонок `metrics_subscribers_daily` не заполняются и
отдаются как нули. Групп-центричная схема меняет смысл DAU/WAU для `kind='user'`:
человек, пользующийся ботом только в группах, больше не создаёт личных событий —
ряды до и после перехода несопоставимы.

## Инструкция по профилю и проверка написанного

- **Ловушка, которую починили.** Явный интерес сверялся с текстом материала
  буквально, а корпус собирается с arXiv, OpenAlex и GitHub и почти весь
  английский: русский термин не совпадал никогда и молча становился постоянной
  нулевой добавкой. Снаружи это неотличимо от «просто ничего не нашлось».
  Теперь одна тема несёт оба написания через `;` — буквальная сверка проверяет
  каждое, вектор грани берёт строку целиком. Для минус-темы это условие работы,
  а не удобство: минус существует только ради буквальной сверки.
- **`services/profile_guide.py`** — один текст инструкции на бота (`/howto`),
  админку (экран `/guide`) и API (`GET /profiles/guide`). Две копии одного
  правила в двух процессах однажды разойдутся.
- **Проверка профиля** (`review`) отвечает не «правильно/неправильно», а «вот
  это работать не будет и почему»: пустое описание, всё скомканное в одну тему,
  русская тема без английского написания, упёрлись в лимит тем.
- **Предпросмотр** (`preview`) показывает, на какие темы разобьётся описание, и
  что не стало темой вовсе. Считает тот же код, который потом будет искать;
  повторять правила разбора на TypeScript значило бы гарантированно с ними
  разъехаться, поэтому в админке живёт прокси-эндпоинт, а не своя реализация.
- Проверка идёт по `compiled_text` — по тому же тексту, что видит поиск.
  Сверять что-то другое значило бы обещать поведение, которого нет.
- Не сделано: экрана `/guide` нет в верхнем меню (на него ведут ссылки из
  карточки профиля и из заявок), и предпросмотр не учитывает несохранённые
  правки явных тем — только описание.

## Групп-центричная схема

- **Субъект разговора — чат, а не отправитель.** `telegram/bot.py::_subject`
  возвращает подписчика по `chat.id`: в группе и канале это сам чат с его общим
  профилем, в личке — человек. Раньше команда в группе заводила отправителю
  личную подписку и показывала ему его собственную выдачу: десять участников —
  десять подписчиков и десять разных ответов в одном чате.
- **Кнопки под материалом чинятся тем же.** Оценка в групповом дайджесте
  привязана к профилю чата, а искалась по подписчику-человеку — и не находилась
  никогда. Снаружи это выглядело как «результат устарел»: обратная связь из
  групп не доходила до обучаемого профиля вообще.
- **Заявка ≠ доступ.** `/start` и `my_chat_member` заводят подписчика со
  статусом `pending`; диспетчер его не видит. Открывает доступ администратор на
  экране «Заявки» одним действием: статус, профиль, пробная подписка и
  сообщение в чат. Отметка о подтверждении живёт в `subscribers.meta.approved`
  отдельно от статуса — статус меняется и дальше, а «пропускали ли этого
  когда-нибудь» теряться не должно.
- **Три правила доступа — одна чистая функция.** `telegram/middleware.py::decide`
  не знает ни про aiogram, ни про базу: на входе тип чата, команда и статус, на
  выходе решение и текст отказа. Поэтому таблица случаев проверяется тестом, а
  не сценарием с поддельными апдейтами (`tests/test_group_centric.py`).
- **Тексты онбординга вынесены в `telegram/onboarding.py`.** Их отправляют два
  процесса: приветствие — бот, сообщение об одобрении — админ-API. Две копии
  одного текста в двух процессах однажды разойдутся.
- **Правка профиля из админки перекомпилирует `compiled_text`.** Прямой UPDATE
  этого не делал: интерфейс показывал новое описание, а ранжирование продолжало
  работать по старому — расхождение молчаливое, заметить его по экрану нельзя.
  Теперь описание и `digest_enabled` идут через сервис профилей, остальные поля
  (параметры доставки, на отбор не влияющие) — напрямую.
- Не сделано: отдельного экрана «профиль группы» вне карточки подписчика нет,
  и уведомления об отказе подписчику не отправляются намеренно.

## Автозапуск и подписчики

- **Чистая база поднимается сама.** `bootstrap/` — три модуля: `schema.py`
  (осмотр схемы и `alembic upgrade head` в отдельном потоке), `seed.py`
  (идемпотентные обязательные записи), `entrypoint.py` (ожидание БД и
  `pg_advisory_lock` вокруг всей операции). Проверено на настоящем PostgreSQL:
  три сервиса, стартующие одновременно на пустой базе, — ровно один мигрирует
  и сидирует, остальные ждут и видят готовую схему. На чистой БД получается 51
  таблица, ревизия `0007` и 370 засеянных записей.
- **Бюджет соединений по образцу `billing_control`.** Движок один на процесс и
  DSN (`get_engine`), пул маленький и с `pool_use_lifo`, `pool_recycle`,
  `pool_timeout`, `command_timeout`. `DB_POOL_SIZE + DB_MAX_OVERFLOW` сверяется
  с `DB_CONNECTION_BUDGET` на старте: превышение — отказ запуска, а не сюрприз
  под нагрузкой. Состояние пула отдаётся в `/ready` и в `geonexa db status`.
- **Dev-режим целиком в compose** — `docker-compose.dev.yml`: PostgreSQL с
  pgvector, отдельная база под метаданные Prefect, сервер и воркер Prefect,
  api, bot, админка. Веса моделей монтируются из `models/` на чтение, в образ
  не пекутся. `DELIVERY_DRY_RUN=true` по умолчанию: очередь работает целиком,
  в Telegram ничего не уходит.
- **Модели ищутся в `models/`** по содержимому каталога, а не только по имени;
  размерность сверяется с `EMBEDDING_DIMENSIONS` до первого запроса.
- **Prefect из админки.** `services/prefect_admin.py` — REST-клиент: список
  деплойментов, запуск, отмена, прогоны, логи, правка расписания. Намерение
  пишется в `schedules` первым, потом уходит в Prefect; если Prefect
  недоступен, строка помечается `sync_pending` и досылается позже. Каталог
  флоу вынесен в `flow_catalog.py` в корень пакета, чтобы admin API не тянул
  Prefect как зависимость ради списка имён.
- **`HarvestMatcher` подключён к пайплайну.** Гейт стоит в `ingestion.py` до
  эмбеддингов; решения пишутся в `harvest_decisions`, счётчики попаданий — в
  `harvest_terms`. Тест доказывает главное: пять нерелевантных материалов не
  доходят ни до эмбеддера, ни до репозитория, ни до LLM.
- **Kind-aware репозиторий** — `db/subscriber_repository.py`: выборки по виду
  подписчика, регистрация групп и каналов, членство бота, подписки с событиями
  и лимитами. Тридцать четыре проверки прогнаны против настоящего PostgreSQL
  (`scripts/check_subscribers.py`), включая три инварианта, которые дороже
  ловить в проде: личный чат нельзя завести как группу, вторая подписка поверх
  первой отклоняется exclusion-ограничением, канал без права постить не
  попадает ни в адресаты, ни в выборку диспетчера.
- **Диспетчеров стало два.** `digest-dispatch` берёт только личные чаты,
  `digest-dispatch-chats` — группы и каналы: у них разные лимиты Bot API,
  разная частота и разная цена ошибки. SQL выборки вынесен в
  `services/dispatch_queries.py` и потому проверяется без Prefect.
- **Два новых флоу**: `chat-monitor` сверяет права бота во всех чатах (Telegram
  сообщает о выходе ровно один раз — пропустив апдейт, мы навсегда считали бы
  чат живым) и `subscription-maintenance` гасит просроченные подписки и
  собирает тех, кому пора напомнить.
- **`container.telegram_bot()`** — один экземпляр `Bot` на контейнер: лимиты
  Bot API считаются на токен, а не на HTTP-сессию.
- **Расписания сидируются из каталога флоу**, а не пишутся руками: разъехавшийся
  каталог давал бы деплоймент без расписания либо наоборот, и заметно это стало
  бы только в проде.
- Тесты: 85 проходят, `ruff check` и `ruff format --check` чисты,
  `alembic check` — «No new upgrade operations detected».

## Вычистка и доводка

Задача была «проверить всё и убрать легаси». Ниже — то, что нашлось; почти
всё из этого видно только на живой системе, а не в тестах с заглушками.

### Отказы, которые ждали в засаде

- **ORM не импортировался без валидной конфигурации.** `db/models.py` звал
  `get_settings()` на импорте, чтобы узнать размерность вектора. Один неверный
  путь к сертификату в `.env` — и весь persistence-слой становился
  неимпортируемым, причём в лицо летело вторичное «Table 'items' is already
  defined»: pytest пробовал импортировать модуль второй раз уже после того, как
  половина таблиц зарегистрировалась в MetaData. Теперь модуль читает две
  переменные напрямую, а настоящая проверка размерности осталась там, где
  ошибиться дороже: в `Settings`, в векторном хранилище и в миграции.
- **`pytest` зависел от `.env` разработчика.** На чистом клоне сбор тестов
  падал. Появился `tests/conftest.py`, фиксирующий окружение; прогон без `.env`
  даёт тот же результат.
- **`LOG_JSON=` ронял старт.** Пустое значение — естественный способ записать
  «по умолчанию», а pydantic отвечал невнятным `bool_parsing`. Пустая строка
  теперь означает «не задано» для всех полей, допускающих None.
- **`geonexa_proxima.api:app` собирался на импорте.** Плюс подмодуль назывался
  `app` и затенял атрибут: сервер мог получить модуль вместо приложения. Модуль
  переименован в `application`, приложение собирается лениво.
- **Мёртвый и сломанный `ItemRepository.save_feedback`** писал в колонку
  `external_user_id`, которой нет с миграции 0003. Его никто не звал — удалён
  вместе с объявлением в порту.
- **Отклонённые материалы не записывались.** Гейт считал их в статистике, но в
  `harvest_decisions` не попадала ни одна строка отказа — а именно они и есть
  материал для калибровки порогов. Тест, который «проверял журнал», сравнивал
  с `>=` и этого не замечал.
- **Гейт не смотрел на журнал публикации.** `venue` не передавался в матчер,
  так что группа приоритетных журналов не могла сработать никогда.

### Настройки, которые врали

Семь переменных были объявлены в `.env` и не читались ни одной строчкой кода.
Администратор менял значение, перезапускал сервис и делал ложный вывод:

| переменная | что теперь делает |
|---|---|
| `LOG_LEVEL`, `LOG_JSON` | модуль логирования существовал, но его никто не вызывал; теперь настраивается в CLI, API и бутстрапе |
| `HARVEST_KEYWORD_THRESHOLD` | перекрывает порог из YAML — калибровка без релиза |
| `HARVEST_STORE_REJECTED` | включает и выключает журнал отказов |
| `HARVEST_DECISION_RETENTION_DAYS`, `METRICS_RETENTION_DAYS` | уборка сырых событий во флоу обслуживания |
| `DELIVERY_RETRY_BACKOFF_SECONDS` | база экспоненциального backoff в очереди |
| `TELEGRAM_GLOBAL_RATE_PER_SECOND` | учитывается вместе с чатовым лимитом |
| `LLM_MAX_RETRIES` | повторы при 429 и 5xx |
| `DEFAULT_LLM_API_KEY` | запасной ключ, если ключ роли не задан |
| `TELEGRAM_WEBHOOK_URL`, `PUBLIC_BASE_URL` | вебхук регистрируется при старте API |
| `DEFAULT_TRIAL_DAYS`, `SUBSCRIPTION_GRACE_DAYS` | пробный период по `/start` |
| `METRICS_ENABLED` | выключатель пересчёта агрегатов |

Оставшиеся неподключёнными (admin API, Prometheus, учёт токенов) перечислены
в `tests/test_settings_coverage.py`. Тест не даёт списку расти незаметно и
требует вычёркивать из него подключённое.

### Бот наконец достижим

- **Пустой allowlist означал «никому».** Свежая установка молча не отвечала
  даже владельцу, а `TELEGRAM_REGISTRATION_MODE` был объявлен и ни на что не
  влиял. Теперь режим решает, владелец проходит всегда, а пустой список в
  режиме `allowlist` считается открытым доступом — с предупреждением в логе.
- **Появился обработчик `my_chat_member`.** До него вся групповая половина
  продукта была недостижима: репозиторий умел заводить чаты, диспетчер умел их
  выбирать, воркер умел в них слать — но никто не создавал ни одной записи.

### Единый словарь

Виды подписчиков и статусы бота были продублированы в трёх местах, включая
литералы внутри SQL. Теперь всё в `domain.py`, а строки CHECK-ограничений и
условия в запросах выводятся из одного источника.

### Чем проверялось

- 108 юнит-тестов, `ruff check` и `ruff format --check` чисты;
- `alembic check` — «No new upgrade operations detected», round-trip
  0001→0005→base→0005 на живой базе;
- `scripts/check_subscribers.py` — 39 проверок против PostgreSQL: подписчики,
  чаты, права бота, подписки, пробный период, выборка диспетчера;
- `scripts/check_delivery.py` — 13 проверок: четыре параллельных воркера без
  пересечений, backoff из настроек (5→10→20→40 с), признание провала, возврат
  зависших заданий, уборка устаревших решений;
- чистая база поднимается с нуля в 51 таблицу и 370 засеянных записей.

## Админка, форматы и курсоры

### Admin API

`api/admin/` — роутеры под `/api/admin`: вход, дашборд, подписчики, чаты,
подписки, профиль сбора, расписания с запуском флоу, реестр моделей,
настройки, доставки, аналитика, аудит и здоровье. 46 GET-эндпоинтов плюс
операции; всё, кроме входа, закрыто зависимостью, навешенной на роутер
целиком — забыть её на отдельном эндпоинте невозможно.

Проверяется скриптом `scripts/check_admin_api.py`: он логинится и дёргает
каждый эндпоинт против настоящей базы. Это нашло семь расхождений со схемой,
которые иначе всплыли бы у администратора в браузере: `payload` вместо
`after` в аудите, `job_id` вместо `delivery_job_id`, `language` вместо `lang`,
`profile_id` вместо `harvest_profile_id`, `status` вместо `state` во
`flow_runs`, нетипизированный `:kind IS NULL` и `gen_random_uuid()` в таблицу
с `bigint`-ключом.

Отдельно нашлись три дефекта поведения:

- **INSERT молча откатывался.** Записи шли через `fetch_one`, а тот открывает
  соединение без транзакции: API отвечал `201` с телом, а строки в базе не
  появлялось. Появился `returning()`, который коммитит.
- **`hmac.compare_digest` падает на не-ASCII.** Вход с кириллическим паролем
  давал 500 вместо отказа. Сравниваем байты.
- **Аудит молча не писался.** `CAST('unknown' AS inet)` падает, а запись
  аудита глотает исключения — записей не появлялось вовсе. Теперь адрес
  проверяется, и невалидный становится NULL.

### Админка на SvelteKit

`admin-ui/` на `adapter-node`, десять экранов, дизайн-код ГЕОНЕКСЫ без
пересчёта токенов. Токен администратора не покидает сервер: страницы
собираются серверными `load`, браузер получает httpOnly-cookie. Графики
нарисованы на голом SVG — чарт-библиотека притащила бы свою палитру и своё
представление о легендах, а дизайн-код задаёт и то, и другое.

Проверено вживую: сборка проходит, все десять экранов отдают 200 с реальными
данными, форма пробы гейта работает, вход и выход работают, страница без
сессии редиректит на `/login?next=`.

### Формат `digest_post`

`services/rendering.py`: карточки с кнопками для лички, один связный пост для
канала. Пост нумеруется сквозным счётом, группируется по видам материалов и
режется по границам материалов — обрыв на середине заголовка читается как
поломка, а не как продолжение. До этого оба канала получали карточки, и
`digest_post` существовал только в списке допустимых значений.

### Курсоры источников

`services/cursors.py`: каждый источник продолжает с водяного знака — времени
самого свежего материала, дошедшего до корпуса, — с нахлёстом в шесть часов.
Без курсоров прогон всегда начинался с фиксированного окна: если сервис лежал
дольше окна, пропущенное не собиралось никогда, а при штатной работе каждый
прогон заново тащил уже собранное.

Курсор только растёт (неудачный прогон не отбрасывает его назад), не уходит в
будущее при сбитых часах и не пытается добрать больше двух недель за раз.

### Восстановлен `pyproject.toml`

Файл содержал только конфигурацию ruff: метаданные проекта и список
зависимостей были потеряны при синхронизации. `poetry install` на репозитории
не работал вовсе. Восстановлен из истории git и дополнен появившимися
зависимостями.

## Разбор логики: что было сломано по существу

Заход по просьбе «посмотреть внимательно, всё ли сделано и логично». Нашлось
семь дефектов, и ни один из них не падал — все они вели себя тихо, а это
дороже.

### Диспетчер слал бы дубликаты на каждом прогоне

`subscriber_profiles.next_digest_at` читался выборкой диспетчера и **никем не
заполнялся**. Условие `next_digest_at IS NULL` было истинно всегда, поэтому:

- при недельном расписании каждый профиль получал дайджест раз в неделю — то
  есть случайно правильно;
- при переводе диспетчера на почасовой запуск (а это заявленная возможность —
  «может чаще недели») каждый подписчик получал бы дайджест **каждый час**.

Заодно `min_interval_hours` из тарифа не проверялся нигде: ограничение плана
было декоративным. Теперь после постановки в очередь профиль получает
`last_digest_at = now()` и `next_digest_at = now() + интервал`, где интервал —
максимум из тарифного минимума и того, что просит профиль. Профиль может
просить реже, но не чаще: иначе ограничение плана обходилось бы правкой
собственных настроек.

Срок двигается сразу после постановки в очередь, а не после успешной отправки:
между ними стоят ретраи, и профиль с временно падающей доставкой иначе попадал
бы в выборку на каждом прогоне и копил дубликаты заданий. Пустой дайджест тоже
двигает срок — иначе диспетчер возвращался бы к профилю без материалов
непрерывно.

### Журнал решений не писался вообще

`decision_sink` объявлен в контейнере и **никогда не создавался**:
`harvest_decisions` оставалась пустой навсегда. От неё зависят экран «почему
отклоняли», калибровка порогов и агрегат воронки — то есть весь разговор про
«через месяц посмотрим и почистим термины» был невозможен.

Там же: `TermHitCounter` не использовался, `hit_count` у всех 323 терминов
оставался нулём, и экран «мёртвые термины» объявил бы мёртвыми все.

Теперь контейнер собирает и журнал, и счётчик, когда есть прогон
(`ingestion_service(run_id=…)`), а флоу сбрасывает накопленные пачки в конце
прогона.

### Обратная связь была недостижима

Кнопки под материалом строил бот — для сообщений, которые человек запросил
командой. Плановый дайджест отправляет воркер доставки, и он слал голый текст.
То есть обучаемый профиль, `profile_item_scores` и выученные интересы не могли
получить ни одного сигнала из основного сценария продукта.

Клавиатура переехала в `telegram/keyboards.py` (обычный словарь, чтобы воркер
не тянул бота), карточка несёт `profile_score_id`, воркер передаёт разметку в
Bot API. У поста в канал кнопок нет намеренно: нажимать их там некому, и
относились бы они неизвестно к какому из двадцати материалов.

### Дайджест навсегда оставался в `queued`

Воркер закрывал задание, но не дайджест. По таблице `digests` нельзя было
отличить доставленное от застрявшего. Теперь `mark_sent` двигает обе строки.

### Аналитика не имела источника

`subscriber_activity` писалась только репозиторием (вступление в чат, смена
подписки). Ни команды бота, ни доставка дайджеста туда не попадали — а на этой
ленте стоят DAU/WAU/MAU и удержание когорт. Задним числом события не
восстанавливаются, так что каждый день без записи терялся навсегда.

Плюс отсутствовал сам агрегат `engagement`: таблица `metrics_engagement_daily`
существовала, эндпоинт аналитики её читал, а писать в неё было некому.

Теперь события пишутся из бота (команда, обратная связь) и из доставки
(`digest_received`), а `ENGAGEMENT_ROLLUP` считает вовлечённость, пустые
дайджесты и средний размер.

### `/ready` прятал пул как раз тогда, когда он нужен

Снимок пула отдавался только при собранном контейнере. Но контейнер не
собирается, если недоступна любая зависимость — например, не скачаны веса
модели, — и именно в этот момент важно понимать, жива ли база. Теперь движок
берётся из процессного реестра, если контейнера нет.

## Открытые вопросы

1. **Реранкер в API-режиме.** Локальный работает через softmax по логитам
   `yes`/`no`. Если поднимать отдельным сервисом — только vLLM `--task score`,
   Infinity или TEI: у GGUF-конвертации реранкера известный баг, после которого
   скоры уходят в район 1e-23. Для эмбеддингов GGUF допустим.
2. **Пароль админки.** Сейчас plaintext в `.env`. Для production сгенерировать
   argon2-хеш в `ADMIN_PASSWORD_HASH` и очистить `ADMIN_PASSWORD`.
3. **Проверить подключение к Timeweb.** Из песочницы до `twc1.net:5432` сети
   нет, поэтому живое подключение не проверено — прогони у себя:

   ```bash
   poetry run python scripts/check_db.py
   ```

   Смотреть на две строки: `btree_gist` (без него не встанет ограничение
   непересекающихся подписок) и `CREATEDB` (если разрешено, Prefect стоит
   выделить отдельную базу вместо контейнера).
4. **Ужесточение профиля сбора.** Текущее `satisfy` пропускает
   инструментальные работы без ML (`geo_sensing`). Если поток окажется
   шумным — убрать `or geo_sensing` из выражения.
